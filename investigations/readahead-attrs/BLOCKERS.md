# Blockers: what was not measured and exactly why

| Lane | Blocker | What it would need |
|---|---|---|
| Real S3 wall-clock for any statement (open latency, throughput at concurrency, ADR-1196's 486 s / 285.8 s contrast) | No AWS credential and no S3 endpoint reachable from this executor; `RAVEL_S3_*` unset. The task named this lane a blocker in advance. | The authorized ClickBench reference host with its loaded tenant and credentials, running `sql_latency_bench --tenant <id> --store s3` with the instrumented binary (`b201bf5525a96844` or a rebuild of this tree). |
| MinIO stand-in | No `docker`, `podman` or `minio` binary on the box (`which` finds none). Not substituted. | Any of the three installed, then `RAVEL_S3_ENDPOINT` pointing at it; still labelled MinIO, never S3. |
| Whole-object versus ranged byte figures under `byte-minimal` on real objects | Follows from the S3 blocker: on the in-process store the ranged path is exercisable (`--logs-fetch-policy byte-minimal`) but its wall-clock is meaningless, and this study kept the stock `cost-based` policy as the declared variable rather than adding a knob sweep. | The same S3 pass at `--logs-fetch-policy byte-minimal`, or in-process for request and byte counts only. |
| Read-ahead prototype measurement | Not built. The checklist in `S5-READAHEAD-CHECKLIST.md` shows it needs the fetch-byte reservation of PR #1284 first, and the in-process evidence (runs 5 and 6) shows it cannot be distinguished from raising the partition count at the same in-flight budget. | #1284 merged; an S3 pass sweeping `--sql-partition-count` at fixed `--store-get-concurrency` to show whether the partition count is the binding limit anywhere. |
| Attribute pushdown prototype | Not built. The design needs a projection-time rewrite of `get_field(attrs, 'k')` into a declared-like per-key column with the divergence rules of S4 preserved; the semantics are pinned by `crates/ravel-sql/tests/attrs_map_vs_declared.rs` but the planner change touches `map_field_planner.rs`, `logs_provider.rs`, `logs_scan.rs` `resolve_columns` and the columnar build, which the four-hour ceiling did not allow after the measurement stages. | A follow-up task; the acceptance criteria are in `WORKITEMS.md` item 1. |
| Cache-warm server behaviour of the planning-path re-fetch | The bench runs with `--cache-bytes 0`; the server has a RAM cache by default, so the 32-of-40 re-fetch measured on the planning path (LEDGER run 3) may be a cache hit on a server whose cache still holds the objects. | Re-run `attrs-declared.corpus.json` with `--cache-bytes 268435456` and read `cache_hits` on the planning-path statements. Ten minutes of work; deferred to the ceiling. |
| CPU attribution by profile (flamegraph) | `ravel-bench`'s `profiling` feature (pprof) was not built into the measured binary. CPU is reported as process CPU time per run (`cpu_ms`, 10 ms resolution) rather than by symbol. | Build with `--features sql-latency,profiling` and set `RAVEL_BENCH_PROFILE_SVG`. |
| GitHub issue and PR state beyond the pasted list | No `gh` token; proxy blocks the API. | Nothing; the pasted list was treated as given. |
