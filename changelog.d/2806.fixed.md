- **The memory gate closes on host available memory, not on the process's
  resident size.** A default-configured server with warm read caches sat
  above the gate's mark (70 % of the memory budget) while the host still had
  9 to 10 GB free, so ordinary work was refused: the ClickBench concurrent
  phase pooled a 0.787 error ratio against 0.071 on v0.23.0, and heavy
  `GROUP BY` statements were refused on a warm server even alone. The
  `ravel-memory-gate` sampler now reads `MemAvailable` from `/proc/meminfo`
  (under a cgroup memory limit, `memory.max` minus `memory.current`) every
  `--memory-gate-interval-ms` and closes the gate while the reading is below
  `--memory-gate-min-available-bytes`, default `max(512 MiB, 2 % of host
  memory)` (687 MB on a 32 GiB host). Below
  `--memory-gate-purge-available-bytes` (default twice the close floor) it
  forces the jemalloc purge, at most once per
  `--memory-gate-purge-min-interval-ms` (default 5000), and re-reads before
  deciding. `--memory-gate-high-water-percent` is removed; it landed in #2764
  and no release carries it. `ravel_memory_gate_high_water_bytes` is renamed
  `ravel_memory_gate_available_floor_bytes`; `ravel_memory_gate_available_bytes`
  (the last available reading) and `ravel_memory_gate_purge_floor_bytes` are
  added; `ravel_memory_gate_resident_bytes` stays the last resident reading.
  The gate's refusal message now names the host's available memory and the
  floor. Startup no longer checks the cache caps against a mark; it refuses a
  purge floor not above the close floor and a close floor at or above host
  memory, and reports `disabled-no-host-memory` when host memory cannot be
  read. For an operator: a warm server on a host with free memory admits
  work, and the gate refuses only when the host itself is close to running
  out.
