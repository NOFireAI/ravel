- **The catalog fold can write per-part key-index leaves for logs and spans,
  off by default.** `ravel-server --fold-key-index-leaves` and `ravel-cli
  catalog fold --key-index-leaves` turn the build on; without either, the
  fold reads no KEY_IDX section, writes no leaf, and writes a part it
  re-encodes without key-index refs. No query uses the leaves yet. With the
  build on, for every part it re-encodes the fold reads each entry's KEY_IDX
  section by ranged GET (a footer suffix, then the section), once per fold
  however many HEAD CAS attempts it makes, and writes one `.kidx` leaf per
  (part, field, key slice) before the part, naming them in HEAD. A logs
  tenant that declares no key-index column and leaves trace-id indexing off
  reads no section and writes no leaf. An entry it cannot index is listed
  as uncovered in the leaf instead of failing the fold, and a failed KEY_IDX
  read GET is logged at warn level with the object key. The tail part is
  re-encoded on every fold that advances the watermark, so with the build on
  each such fold reads the section of every entry in the tail. The fold
  report (and `ravel-cli catalog fold`) gains `key_index_ranged_gets` and
  `key_index_bytes_read` (the total the fold issued), and
  `key_index_leaves_written`, `key_index_leaf_bytes_written` and
  `key_index_uncovered_entries` (for the attempt that published);
  `ravel-cli catalog inspect` prints each part's `key_index (field 8)` refs.
  The catalog sweep keeps every leaf HEAD names, deletes unreferenced leaves
  past the protection horizon, and reports its deletes by kind as
  `ravel_maintain_catalog_objects_deleted_total{kind="csnap|npost|cstat|kidx|other"}`.
