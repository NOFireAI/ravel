- **The query guide and HTTP reference say a failed catalog decode job still
  answers exactly** (issue #2402). Both documents said a catalog decode job
  the read CPU gate cancelled at shutdown answered 503 and one that panicked
  answered 500. Neither does: a snapshot part falls back to listing, postings
  disable pruning, and column statistics degrade to a scan, so the query
  answers exactly by the slower path. The 503 and 500 entries now name the
  segment decode job, which is the decode that answers them. A column-stats
  decode job that panicked or was cancelled is no longer counted as a
  column-statistics decode refusal: it leaves the refusal counter flat and no
  longer silences the warning a later genuine refusal of the same object would
  log. A cancelled job warns on every occurrence, since a retry can succeed. A
  panicked one panics again on the same bytes, so it warns once per object key
  and is counted on every occurrence in the new
  `Catalog::column_stats_decode_panics`.
