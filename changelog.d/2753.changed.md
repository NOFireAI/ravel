- **`ravel-cli load` writes objects of about 250,000 rows by default, on
  logs, metrics and spans.** With `--target-bytes` unset the flush target is
  derived as 250,000 rows times the first batch's estimated bytes per row,
  and with `--pipeline-depth` unset the depth is derived as the lowest of
  ceil(250,000 x `--shards` / `--batch-rows`), the memory bound
  (`--load-memory-bytes` divided by the estimated object bytes of one batch,
  at least 1) and 1,024. With the target derived, the loader flushes every
  shard (`flush_all`) once the oldest batch pending on any shard is
  `--pipeline-depth` batches old; a size flush restarts only its own shard's
  window, and an explicit `--target-bytes` turns that depth flush off. At the
  previous defaults a 510,000-row single-shard load wrote 51 objects; it now
  writes 3. The loader prints the resolved target and depth as one
  `load geometry:` line on stderr before the first write, and every signal's
  summary prints them with what decided each, whether the depth window kept
  realigning on size flushes (`realign_gave_up` in the JSON), the flush
  trigger mix (size, age, arrival, depth, manual), the `--target-bytes` no-effect
  warning when it applies, and the same report as one `load report json :`
  line. Three behaviors change beside the layout: an unset
  `--max-flush-delay` now reaches the router as 60s instead of the router's
  2s default; the end-of-input `flush_all` runs after `wait_enqueued`, so it
  covers every submitted write; and a load that fails on a refused row or a
  failed write flushes its buffered writes before it waits on them, so it
  reports without waiting out the age trigger. To get one object per batch
  per shard and four writes in flight, pass `--target-bytes 1
  --pipeline-depth 4` with an explicit `--batch-rows`.
