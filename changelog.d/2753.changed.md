- **`ravel-cli load` writes objects of about 250,000 rows by default, on
  logs, metrics and spans.** With `--target-bytes` unset the flush target is
  derived as 250,000 rows times the first batch's estimated bytes per row,
  and with `--pipeline-depth` unset the depth is derived as
  ceil(250,000 x `--shards` / `--batch-rows`), lowered to the memory bound
  (`--load-memory-bytes` divided by the estimated object bytes of one batch,
  at least 1) when that is smaller, and capped at 1,024. With the target
  derived, the loader flushes a shard once `--pipeline-depth` batches have
  been submitted since that shard's last size flush; an explicit
  `--target-bytes` turns that depth flush off. `--max-flush-delay` now
  defaults to 60s on every signal. At the previous defaults a 510,000-row
  single-shard load wrote 51 objects; it now writes 3. The loader prints the
  resolved target and depth as one `load geometry:` line on stderr before
  the first write, and every signal's summary prints them with what decided
  each, the flush trigger mix (size, age, depth, manual), the
  `--target-bytes` no-effect warning when it applies, and the same report as
  one `load report json :` line. A failed load flushes its buffered writes
  before it waits on them, so it reports without waiting out the age
  trigger. To restore the previous one-object-per-batch-per-shard layout and
  write concurrency, pass `--target-bytes 1 --pipeline-depth 4` with an
  explicit `--batch-rows`.
