- **The Kubernetes operator keeps the fragment NetworkPolicy until the query
  rollout completes, and a distributed-query Secret rotation rolls the query
  pods** (issue #2403). Disabling distributed query used to delete the
  `<cluster>-query-fragment` NetworkPolicy as soon as the new query Deployment
  was applied, leaving port 4319 on the old pods reachable from the namespace
  for the rest of the rolling update. The delete now waits until the query
  Deployment's `status.observedGeneration` equals its `metadata.generation`,
  `status.updatedReplicas` equals `status.replicas`, `status.unavailableReplicas`
  is zero or absent, and `status.terminatingReplicas` is zero when the cluster
  reports it, so the policy is not deleted while an old pod is still terminating
  on the fragment port. A change that narrows the policy while distributed query
  stays on, such as turning `spec.probes.dedicatedHealthPort` off, keeps the
  wider policy until the same condition holds, and disabling distributed query
  mid-rollout now holds that wider policy too so a port the new pods open is not
  blocked. The four distributed-query Secrets' `resourceVersion`s now feed the
  query pod template's secrets checksum, so rotating a fragment certificate, CA
  or key file, or the SQL ticket key, rolls the query pods without a manual
  `kubectl rollout restart`; the first reconcile after the upgrade rolls the
  query pods once on a cluster with distributed query enabled. When one of
  those Secrets is missing from the namespace, the operator now holds back the
  query Deployment, with a `Degraded` condition naming the Secret, instead of
  rolling the query Deployment onto pods that cannot start; the running query
  pods keep serving, the NetworkPolicy stays in place, and the gateway and
  maintain Deployments reconcile as usual. The operator reads only the
  metadata of these Secrets, never their values.
