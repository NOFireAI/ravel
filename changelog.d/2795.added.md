- **`--sql-scan-decode-inline` puts the SQL `logs` and `spans` scan-block
  decode back on the polling worker** (env `RAVEL_SQL_SCAN_DECODE_INLINE`,
  default off). When set, those two scans decode their blocks inline instead
  of on the read CPU gate, as before ADR-1702 follow-up task 8, and every gate
  site their fetchers use (`log_block`, `log_postings`, `log_section` and
  `span_block`) counts nothing for SQL statements. The catalog,
  PromQL, maintenance and SQL `samples` gate sites keep the gate. Startup logs
  which mode the SQL scans run in. The flag exists to A/B the gate's cost
  against its liveness benefit (issue #2795); setting it gives up the
  isolation the gate gives scans.
- **`--cpu-gate-read-dispatch in-place` runs read CPU gate jobs on the calling
  worker** (env `RAVEL_CPU_GATE_READ_DISPATCH`, values `spawn-blocking`, the
  default, and `in-place`). With `in-place` the read gate still takes a permit
  for each job, so the permit count still caps how many run at once, but runs
  the job through `tokio::task::block_in_place` instead of `spawn_blocking`:
  the decoded output stays on the worker that asked, and the runtime moves that
  worker's other queued tasks to another thread while the job runs. The write
  gate keeps the blocking pool. A job that cannot block in place (a runtime
  that is not multi-threaded, or a `LocalSet`) runs on the blocking pool and
  counts in the new `ravel_cpu_gate_in_place_fallback_total{gate}`. Startup
  logs the read gate's mode. Experimental, for the issue #2795 A/B.
