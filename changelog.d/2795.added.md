- **`--sql-scan-decode-inline` puts the SQL `logs` and `spans` scan-block
  decode back on the polling worker** (env `RAVEL_SQL_SCAN_DECODE_INLINE`,
  default off). When set, those two scans decode their blocks inline instead
  of on the read CPU gate, as before ADR-1702 follow-up task 8, and every gate
  site their fetchers use (`log_block`, `log_postings`, `log_section` and
  `span_block`) counts nothing for SQL statements. The catalog,
  PromQL, maintenance and SQL `samples` gate sites keep the gate. Startup logs
  which mode the SQL scans run in. The flag exists to A/B the gate's cost
  against its liveness benefit (issue #2795); setting it gives up the
  isolation the gate gives scans.
- **`--sql-scan-blocks-per-job` decodes several SQL `logs` scan blocks per
  read CPU gate job** (env `RAVEL_SQL_SCAN_BLOCKS_PER_JOB`, default 1, 0
  refused at startup). Above 1, one `log_block` job of the scan's columnar
  path decodes up to that many consecutive blocks of a segment, paying the
  gate's per-job handoff once for all of them, and stops early at the end of
  the segment or of a row group, at a block the TopK threshold skips, at a
  block that falls back to the row path, or once its built batches reach
  32 MiB. The query returns the same rows. `ravel_cpu_gate_jobs_total` and
  `ravel_cpu_gate_inline_total` for `log_block` then count these jobs, not
  blocks. Startup logs the value beside the scan decode mode (ADR-1702,
  blocks-per-job amendment).
