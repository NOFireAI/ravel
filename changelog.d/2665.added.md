- **`GET /api/v1/alerts`, and real health and state on `GET /api/v1/rules`.**
  The alert evaluator publishes a per-tenant snapshot at the end of each tick,
  and both routes render it in the Prometheus shapes. `/api/v1/alerts` lists
  the caller's pending and firing alerts with `labels`, `annotations`,
  `state`, `activeAt` and `value`; suppressed and resolved alerts are left
  out. `value` is the matched sample, or the row count for a SQL rule, and is
  present only when this process held the tenant's lease on the last tick and
  evaluated the rule without error. Each rule on `/api/v1/rules` now carries
  `health` (`ok`, or `err` with `lastError`), `lastEvaluation`, `state`
  (`inactive`, `pending` or `firing`) and an `alerts` array. Neither route
  reads object storage or runs a query, and neither reads another process's
  state: before this process's first tick, and in a process that runs no
  evaluator, rules read `unknown` and `/api/v1/alerts` answers 503 rather than
  an empty list. When the last tick could not read alert history, rules read
  `err` health and `unknown` state and `/api/v1/alerts` answers 503 until a
  tick reads it again, rather than serving an earlier tick's list. History
  stays on the `alerts` SQL table (ADR-1101 amendment).
