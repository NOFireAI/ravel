- **SQL resolves duplicate samples on compacted data the way PromQL does.** On
  a run that merged several writes' samples, the SQL `samples` scan stamped
  every row with the run's shared provenance and on-disk position instead of
  the sample's own dedup key from the per-sample provenance column, so at a
  duplicate `(series, ts)` SQL could return a different value than PromQL for
  the same sample. The scan now carries each sample's own key, and
  `RsegDedupExec` resolves it with the same `serves_over` order the PromQL
  merge uses. A per-sample column whose length disagrees with its run now
  fails the query instead of being truncated.
