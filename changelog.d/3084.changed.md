- **`--cache-bulk-scan-min-bytes <BYTES>` reads filtered `logs` statements
  larger than the cache as bulk scans** (ADR-3072's size trigger amendments).
  It applies to `logs` statements sent as SQL text, through
  `POST /api/v1/sql` or as an alert rule's SQL; default unset, which keeps the
  predicate-free rule alone. Set, such a statement is also a bulk scan when it
  names one `logs` table and no Parquet table, its optimized plan has no
  equality on a field the tenant indexes in KEY_IDX, and the last successful
  execution of the same SQL text for the same tenant read at least the
  threshold (bytes served from the cache plus bytes read from the store, every
  phase). Its first execution in a process therefore reads as interactive, and
  a statement whose text changes every run never reads as bulk. The process
  keeps that record for the 4,096 most recent statements. The threshold in
  force is the flag raised to `--cache-max-bytes` when that is larger, and
  startup logs it as a `performance default resolved` line with
  `setting="cache_bulk_scan_min_bytes"` and a `source` of `flag` or
  `flag-floored-to-cache-max-bytes`. A bulk scan's reads go to the fetcher
  cache's bulk region (`--cache-bulk-share`) instead of the interactive
  queues, and `stats.cache.intent` reports `bulkScan`. `samples` statements and
  lowered ES|QL statements are unaffected. Rows returned are unchanged.
  `sql_latency_bench --cache-bulk-scan-min-bytes` applies the same floor at
  `--cache-bytes`.
