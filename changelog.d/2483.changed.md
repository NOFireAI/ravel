- **`ravel-server`'s process memory budget now starts from available memory,
  not raw total (ADR-1170, amended 2026-10-03 by issue #2367, issue #2483).**
  With no cgroup memory limit and a readable `MemAvailable` in
  `/proc/meminfo`, `memory_budget_bytes` resolves to `min(MemTotal - RESERVE,
  max(FLOOR, MemAvailable + own RSS - RESERVE))`, logged with
  `source="derived-available"`; `FLOOR` is a 1 GiB floor below which the
  budget never derives, and binding it logs a `WARN` naming the `MemAvailable`
  reading and `--memory-budget-bytes` as the remedy. A cgroup memory limit
  keeps the pre-amendment rule unchanged (`source="derived-cgroup"`,
  `MemAvailable` not consulted), and an unreadable `MemAvailable` (including
  every non-Linux build) also keeps the unchanged `MemTotal`-minus-reserve
  rule (`source="derived"`). The new `--memory-budget-bytes` flag (env
  `RAVEL_MEMORY_BUDGET_BYTES`) overrides every derivation outright and is
  still subject to the existing too-small-budget startup refusal. A derived
  (not explicit-flag) `--sql-max-query-bytes` or `--sql-tenant-max-bytes` is
  additionally held at or below 90% of the shared SQL/fetch remainder,
  logged beside the existing `clamped`/`raised` fields as
  `remainder_capped`; an explicit flag on either is never capped. A host with
  co-resident processes claiming memory this server cannot see now derives a
  smaller budget, and smaller caches and SQL pools with it, than it did
  before this change.
