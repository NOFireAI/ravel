- **`--store-get-concurrency` now derives from the memory budget, and a
  loopback store defaults to `latency-first`** (ADR-2677 decision 7, issue
  #2683). Unset, the GET permit count is 60% of `memory_budget_bytes` divided
  by 64 MiB, clamped to 8..=256, so a 32 GB host resolves 256 where it used
  to resolve `max(8, 2 x cores)` (32 on 16 cores), and a 16 GiB host 134. The
  startup line reports source `budget-share` with the budget, share,
  per-permit bytes and ceiling it used. A host with no readable memory, and a
  gateway, keep the core derivation. `--sql-partition-count` and
  `--promql-fetch-fanout` are unchanged. With `--logs-fetch-policy` unset, a
  `--store s3` deployment against a loopback `--s3-endpoint` now resolves
  `latency-first` (source `default-loopback`) instead of `cost-based`; a
  remote endpoint still resolves `cost-based`. An explicit
  `--store-get-concurrency`, `--fetch-concurrency` or `--logs-fetch-policy`
  wins as before; set `--logs-fetch-policy cost-based` to keep the earlier
  loopback read shape.
