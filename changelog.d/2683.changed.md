- **`--store-get-concurrency` is now sized from the memory budget on every
  store kind, and a loopback store defaults to `latency-first`** (ADR-2677
  decision 7, issue #2683). Unset, the GET permit count is 64% of
  `memory_budget_bytes` divided by 64 MiB, rounded down and clamped to
  8..=256. The 64% is chosen so the 32 GB reference host's recorded budget,
  27,775,004,672 bytes, derives 256 with margin: 256 needs a budget of at
  least 26,843,545,600 bytes (25 GiB). On the 16-core reference host the
  default moves from `max(8, 2 x cores)`, 32, to 256, for remote stores as
  well as loopback ones; a 14 GiB budget resolves 143, 6 GiB 61 and 3 GiB
  30. A real Linux host derives its budget from `MemAvailable`, so read the
  startup line rather than a table built on `MemTotal`. The count bounds concurrent GETs, not bytes: each fetch reserves its
  object's bytes on the memory budget before it takes a permit, and the
  budget refusing a fetch it cannot hold (HTTP 503, `upstream storage
  temporarily unavailable`) is what bounds them. The SQL ranged fast path's
  per-partition prefetch share, `max(2, store_get_concurrency /
  sql_partition_count)`, follows the permits, from 2 to 8 on the reference
  host. The startup line reports source `budget-share` with the budget,
  share, per-permit bytes and ceiling it used. A host with no readable
  memory, and a gateway, keep the core derivation. `--sql-partition-count`
  and `--promql-fetch-fanout` are unchanged. With `--logs-fetch-policy`
  unset, a `--store s3` deployment against a loopback `--s3-endpoint` now
  resolves `latency-first` (source `default-loopback`) instead of
  `cost-based`; a remote endpoint still resolves `cost-based`. An explicit
  `--store-get-concurrency`, `--fetch-concurrency` or `--logs-fetch-policy`
  wins as before. To keep the earlier read shape, set
  `--store-get-concurrency` to the earlier `max(8, 2 x cores)`
  (`--store-get-concurrency 32` on 16 cores), and on a loopback store also
  `--logs-fetch-policy cost-based`.
