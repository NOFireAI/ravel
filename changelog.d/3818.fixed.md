- **A metrics fetch over a large compacted segment no longer reserves more
  than its share of the fetch memory budget at once** (#3818). Coalescing
  within the 64 KiB gap, and on L0 objects bridging down to 4 page runs, could
  join the small pages a query selected into one run spanning most of a
  segment, and the whole run was reserved against the fetch budget, so a query
  whose needed bytes fit could be refused with `fetch memory exhausted`.
  Neither step now joins needed ranges into a run longer than the budget's
  limit divided by the GET concurrency, or 8 MiB when that share is smaller; a
  single needed range longer than that is still fetched whole in one GET
  (`coalescing_never_builds_a_run_past_the_fetch_share`,
  `bridging_never_builds_a_run_past_the_fetch_share`,
  `the_cap_never_splits_a_needed_range`). An L0 fetch of an object longer
  than that cap, so never one of 8 MiB or less, can now issue more than 4
  page GETs (`max_run_len_is_the_per_get_share_with_a_floor`). Runs that were
  each under the cap were still reserved as one summed total, so a fetch of
  many of them could be refused the same way; the runs are now reserved and
  fetched in batches of at most that cap (or one longer run alone),
  each batch's reservation released before the next is taken, so one fetch
  never holds more than one batch reserved
  (`one_call_never_reserves_more_than_one_batch`). The GETs issued and the
  bytes they move are unchanged (`batching_keeps_the_gets_and_wire_bytes`);
  batches are fetched one after another, so a fetch spanning several batches
  takes one round trip per batch.
