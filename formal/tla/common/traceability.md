# Traceability: RavelObjectStore invariants to their Rust source

Each row maps a TLA+ action or property in `MCRavelObjectStore.tla` /
`RavelObjectStore.tla` to the object-store contract behavior it pins, to the
Rust symbol that implements that behavior, and to the contract test that
exercises it (ADR-1113 D8). `scripts/check-tla.sh traceability` resolves the
Rust references: a reference is `crates/<path>.rs::Sym1::Sym2...`, and the
check requires the file to exist and every `::`-separated symbol to appear in
it. A reference to a `.tla` file is rejected: a traceability row must cite the
implementation, not the model. The "new test needed" column names a gap where
no contract test exists yet, or `none` when the existing test covers it.
The "Antithesis property" column (ADR-4326 decision 6) names the assertion
message the store-contract workload's driver (`antithesis/store-contract/`)
checks for the row against RustFS through `S3Store`;
`antithesis-mutants.tsv` maps each `negative/*.cfg` to the driver-side mutant
that must make that property false.

| Delete / VersionsNeverReused | The version counter is never reset by a delete, so create/delete/create mints a fresh version and a CAS holding the pre-delete version fails. The store-contract driver checks this contract as Ravel uses it, which the TLA+ global counter overstates for a backend whose version is a content ETag: with different bytes the recreate's version differs and a CAS holding the pre-delete version is refused (the assert_always this row names); with identical bytes S3Store returns the same ETag, so the driver does not require the version to differ (it records whether it did with the assert_reachable "store: a same-bytes recreate ran", whose details carry reused true or false) and instead checks that the same-bytes CAS outcome matches its effect, asserted as "store: a CAS holding a pre-delete version matches its effect after a same-bytes recreate". The cas-accepts-stale-version mutant refutes that sub-check only when the recreate's version differs from the first (V2 != V1); on RustFS, where V2 == V1, the mutant's overwrite is answered Ok and stores the CAS bytes, as a valid CAS would, so the sub-check passes and the mutant is refuted by the different-bytes assert_always this row names. Each CasVersion target in the ravel-maintain crate that is also deleted carries a field that changes between the write a stale holder read and a recreate: the migrate cursor a per-write nonce since #4389 (crates/ravel-maintain/src/migrate.rs::CursorNonce, written by write_cursor and ContradictionStamp::encode), the certify cursor its census start time (crates/ravel-maintain/src/compat_certify.rs::encode_cursor, start_unix_ns); no code in the repository deletes the compaction scan cursor (crates/ravel-maintain/src/scan.rs::write_cursor) or sys/gc (crates/ravel-maintain/src/gc_config.rs::GC_CONFIG_KEY) | crates/ravel-object-store/src/memory.rs::next_id | crates/ravel-object-store/tests/contract.rs::assert_cas_version_semantics and crates/ravel-object-store/tests/contract.rs::cas_with_pre_delete_version_fails_after_recreate | none | driver: store-contract -- store: a version is never reused after a delete |

| PutOverwriteLostResponse / LostResponseEffectApplied | A lost-response write applied its durable effect even though the caller observed Failure. On the real store the store-contract driver's lost-response action is a plain acknowledged overwrite whose response the caller drops, so its assert_always ("store: a lost-response overwrite took effect") checks only that an acknowledged write is applied (read-after-write); the genuine lost-response case, where the caller saw a failure but the write still landed, is the transient action's reachable "store: a failed write was later found applied". | TransientFailure / TransientLeavesNothing | A transient failure applies nothing and returns a retryable Failure, so the caller retries the identical operation.
