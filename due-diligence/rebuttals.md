# Adversarial synthesis: falsification attempts on Critical and High findings

Method: for every P0/P1 finding a different reviewer (the panel chair with targeted code reading, or a dedicated skeptic agent) attempted to falsify it; the original evidence then had to survive the attempt. Each entry records the finding, the falsification attempt, the defense, and the resolution. Unresolved disagreement is preserved explicitly.

## R1. Memo B finding 1 (P1): orphan GC converts out-of-band commit-record loss into permanent deletion of acknowledged data

Falsification attempts:

1. "The scrub (ADR-0059) would detect the loss before the 25 h orphan gate fires." Checked: crates/ravel-maintain/src/scrub.rs walks objects identified by their CommitRecord (scrub.rs:10-13), so it verifies data-object integrity given a record; it cannot see a missing record at all. The scheduled scrubber (services/ravel-server/src/lib.rs:328-335, default period 7 days) does not close this. Attempt fails.
2. "`ravel-cli catalog verify` alarms on the state." Checked: verify (services/ravel-cli/src/catalog.rs:176-234) reports snapshot entries with no matching commit record but deliberately never fails on them, because retention legitimately produces that shape after folding. Detection exists only as non-failing report lines on an operator-run command. Attempt fails.
3. "The trigger is outside the store contract, so this is not a Ravel finding." Partially sustained: the trigger (lifecycle rule, prefix delete, persistent LIST omission) is external. But Ravel's sweeper is what converts recoverable metadata loss (data objects still present, reconstruction CLI exists) into unrecoverable data destruction, silently when below the breaker thresholds (50 count AND 10% ratio). The system's own ADR-0058 calls it the most dangerous flaw in the durability posture.

Resolution: P1 stands, scoped precisely: not a bug in the commit protocol, but a hazard amplifier in the deletion path with a detection gap below breaker thresholds. The window (grace + max_flush_lifetime, ~25 h) is the operator's entire reaction time, and nothing in-system alarms during it below the breaker. Recommended fix (report section 27): alarm on every orphan deletion batch above a small floor, and offer a quarantine-instead-of-delete mode (move to a `quarantine/` prefix for a second horizon) so the reaction window survives the sweep.

## R2. Memo C finding 1 (P1): compaction published more than 26 h behind the fold watermark poisons the folded snapshot; the superseded-input sweep then makes it a persistent 503

Falsification attempts:

1. "The re-resolve after SnapshotInvalidated falls back to listing and heals." Checked: the engine re-resolves exactly once (crates/ravel-query/src/engine.rs:1077-1142) and the re-resolve reads the same durable HEAD through resolve_snapshot_window's head cache (crates/ravel-catalog/src/snapshot_resolve.rs:359, 601-654); the fallback-to-listing path triggers on HEAD/part read failure, not on a resolved snapshot whose entries later 404. No healing path exists until a fold re-lists the hour, which the fixed 26 h window never does. Attempt fails.
2. "The maintain process forces a fold invalidation when it publishes a compaction record." Checked ADR-0065's invalidate hook: it drives maintain's own zone memoization, not the catalog fold's reconcile window. The fold's only triggers are the fixed window and the retention frontier band (fold.rs:949-1034). Attempt fails.
3. "catalog verify detects it." Same result as R1 attempt 2: entries with no commit record are reported but non-failing; worse, in this state data keys are reconstructed from snapshot entries without commit-record GETs, so the first user-visible signal is 503s. Attempt fails.
4. "The pinning test proves the project intends this, so it is a documented tradeoff, not a bug." Rejected: the test (fold.rs:3507-3557) pins the reconcile-window behavior, and the config comment (config.rs:76-85) claims safety under an assumption (record target hour within 26 h of watermark at publish) that nothing enforces; the sweep half of the interaction has no test at all. A documented tradeoff whose stated safety argument does not hold under ordinary operations (first maintain enablement on existing history, a one-day maintain outage) is a defect.

Resolution: P1 stands. Availability/visibility, not data loss (L1 parts conserve every sample; token reads unaffected). Blast radius: every non-token query touching the affected hours, persisting for weeks (retention-window tenants) or indefinitely (no-retention tenants). The asymmetry against retention's HEAD gate (retention.rs:563-577 vs sweep.rs:479-501) shows the fix shape already exists in-tree.

## R3. Memo C finding 2 (P1): erasure `.done`/`.dreq` lifecycle can re-serve erased-subject records from a stale folded snapshot

Falsification attempts:

1. "ADR-0064's completion gate resolves through the same resolver a query uses, so it cannot under-assert." Checked: the gate (erasure_rewrite.rs:1990-2115) resolves the live listing view; a query resolves the folded snapshot when the hour is at or below the watermark. Outside the reconcile window these two views diverge, which is exactly the case ADR-0064's own correction (0064:340-354) records as open. The gate satisfies only the weaker branch of the ADR's stated requirement. Attempt fails.
2. "The `.dreq` sweep waits for the protection horizon, which covers the stale window." Checked: the horizon anchors on `.done` created time plus protection_horizon (sweep.rs:1340-1390); the stale folded snapshot's lifetime is unbounded (until a fold re-lists the hour), so no horizon arithmetic covers it. Attempt fails.
3. "This requires erasure of data older than 26 h behind the watermark, which is rare." Rejected as mitigation: DSAR requests are mostly about historical data; the out-of-window case is the common case for erasure, not the corner.

Resolution: P1 stands for deployments using selective erasure for regulatory obligations; inapplicable otherwise. The compliance guarantee ("no query whose snapshot resolves after the request ack returns matching records") holds while the `.dreq` lives; the defect is that `.done` and the `.dreq` sweep can retire the filter while a stale snapshot still resolves pre-rewrite inputs. Same root cause as R2 (fold reconcile window); one fix addresses both.

## R4. Memo D finding 1 (P0): binary operators silently degrade native-histogram operands to float 0.0

Falsification attempts:

1. "The 91/91 differential run against real Prometheus would have caught wrong values on a binop; a green run refutes the finding." Checked the corpus directly (crates/ravel-promql-difftest/corpus/binop.txt and histogram_native.txt): no corpus entry applies a binary operator to a native-histogram operand. The only `kind: range` histogram entries wrap the series in `histogram_quantile`/`fraction`, which is the one guarded path that re-runs on the instant evaluator per step. The differential is strict (`f64::to_bits` equality) and end-to-end, but it cannot detect a defect it never exercises. The green run and the finding are both true. Attempt fails; it strengthens the finding by explaining why an otherwise-trustworthy signal is blind here.
2. "Histogram elements never reach the binop path, so the concern is moot." Checked: `eval_vector_selector` places histogram elements into the same instant vector as floats, carrying `value: 0.0` with `histogram: Some` (eval.rs:91-137, 816-832); `eval_scalar_vector`/`one_to_one` read `s.value`/`l.value`/`r.value` and emit `histogram: None` (binop.rs:139-190). The element reaches the path and its zero value is used. Attempt fails.
3. "This is an intended, documented limitation (approximation opt-in and visible)." Rejected: the repo invariant is that approximation is opt-in and visible, and the subquery path already implements the visible form of exactly this refusal (`Unsupported: subquery over native histograms`, eval.rs:940-960). Binop returns a wrong numeric answer with HTTP 200 and no warning. That is silent approximation on a critical path, which the invariants forbid; the asymmetry with the subquery guard proves it is an omission, not a decision.

Resolution: P0 stands, scoped to tenants that ingest native histograms and apply arithmetic, comparison, or ratio operators to them (a mainstream OTLP pattern). Wrong values, not unavailability. The fix shape exists in-tree: apply the subquery path's typed refusal to the binop path, or implement real histogram arithmetic. Severity is P0 because the output is silently incorrect data an operator cannot distinguish from a real zero, and it feeds alerting (attempt scenario: a histogram-side ratio that never crosses its threshold).

## R5. Memo D finding 2 (P0): range queries with a top-level aggregate/binary over native histograms return a matrix of zeros

Falsification attempts:

1. "The instant-path histogram support means the grid reducer sees live histograms, so the result is correct." Checked: the per-step instant evaluation does produce histogram elements, but `eval_instant_over_grid` then reads only `s.value` when assembling the matrix (eval.rs:704-711, functions/mod.rs:558-602 reads `s.value` at 571-580). The histogram is alive right up to the reducer and is discarded there. The liveness of the intermediate value is what makes the zeros look plausible. Attempt fails.
2. "`histogram_quantile(0.99, sum(rate(h[5m])))` works, so range queries over histograms work." Checked: that specific call works because `HistogramQuantile`/`Fraction` range evaluation re-runs the whole call on the instant path per step (functions/mod.rs:446-476), bypassing the flattening reducer. `sum(rate(h[5m]))` without the quantile wrapper does not. The working case is a narrow escape, not the general path. Attempt fails, and the narrowness makes the defect more deceptive (the canonical dashboard query works while the plain aggregate does not).
3. "A user would notice a flat zero line and investigate." Rejected as mitigation: a flat zero line on a histogram-derived panel is indistinguishable from a genuinely idle metric; capacity and SLO decisions are made on exactly this shape. HTTP 200 with no warning gives the operator no signal to investigate.

Resolution: P0 stands, same tenant scope as R4. Wrong values (a matrix of zeros) on `/api/v1/query_range`, the surface every Grafana time-series panel uses. Same root class as R4 (value-only reduction over an element whose value field is documented meaningless); one design fix (make the reducers histogram-aware or refuse typed) addresses R4, R5, and the P1 range-selector/over_time omissions together.

## R6. Memo E finding 1 (P1): PromQL parser/evaluator has no recursion-depth or query-length guard, enabling a stack-overflow DoS on the shared query process

Falsification attempts:

1. "The `tokio::time::timeout` around evaluation (engine.rs:430) bounds the query, so a pathological query is cut off, not fatal." Checked: a stack overflow is not a slow future the timeout can pre-empt; it aborts the thread with SIGABRT before the timeout fires, and SIGABRT is not catchable by `catch_unwind`. The timeout bounds wall-clock of a running future, not stack growth. Attempt fails.
2. "The 1 MiB body cap bounds the query, so depth is bounded to something safe." Checked: the cap bounds body bytes (http/handlers.rs:31), and AST depth is proportional to body length for nested parens/unary (`((((...` or `----...`), so 1 MiB of body yields an AST on the order of hundreds of thousands deep, well past a 2 MiB default worker stack for a recursive parse/check/eval/drop. The cap is the wrong bound: it limits width of input, not depth of recursion. Attempt fails.
3. "Some existing budget (max_series/max_samples/subquery grid) already limits recursion." Checked: those budgets bound evaluation width and point counts (config.rs:8-11), not AST depth; a grep for depth/recursion guards in ravel-promql and ravel-query finds none on the parse/eval/drop path. Attempt fails.
4. "It was not executed, so it is speculative." Partially sustained on the letter (the exact overflow depth was not measured, so the label is STRONGLY SUPPORTED, not VERIFIED), rejected on the substance: the four ingredients (reachable 1 MiB body, recursive-descent AST, recursive evaluator with no counter, synchronous execution on the shared worker) are each individually confirmed by code, and their composition is a standard stack-overflow vector. The uncertainty is the precise depth, not whether the vector exists.

Resolution: P1 stands. Availability, not correctness or data loss: a single unauthenticated-to-the-tenant-surface query aborts the query process and takes every concurrent tenant's in-flight query with it, on a multi-tenant shared surface. Distinct in kind from R1-R3 (which are durability/visibility/compliance); this is the one shared-process crash-DoS in the review. Cheap fix (byte-length cap far below 1 MiB, or an explicit AST-depth check before evaluation, or a guarded stack), so it is a low-cost, high-blast-radius item for the exit-criteria list.

## R7. Memo G finding 1 (P1): the native-histogram silent-failure family extends beyond the R4/R5 binop and grid cases to range selectors, rate/increase/delta in range mode, the over_time family, comparisons, and topk/quantile

Falsification attempts:

1. "This is the same finding as R4/R5, already resolved; no new record needed." Rejected on scope: memo G reproduced the family empirically against the real evaluator (a probe over ravel-promql's public Evaluator and its own histogram-capable TestSource) and found silent behaviors R4/R5 did not cover: range `rate(h[5m])` returns a correct histogram vector on /api/v1/query and an empty matrix on /api/v1/query_range (functions/mod.rs:415-444, the range arm reduces floats only while the instant arm unions in the histogram reduction); bare `h` as a range query returns empty because the matrix type cannot carry histograms (eval.rs:146, json.rs:278-281); over_time functions return silently empty; comparisons produce phantom series from the 0.0 placeholder. Each is a distinct silent path, and one (`absent_over_time(h[15m])` returning 1 while data flows) turns a liveness alert into a permanent false positive.
2. "The probe is not the production path; the server might behave differently." Checked: the evaluator is the shared component between probe and server, the difftest corpus header records a confirmed end-to-end run (ingest through RSEG through the evaluator against real Prometheus), and `MergedSource` implements the histogram read path the server uses (engine.rs:2749). The residual gap (no full-server MinIO reproduction) is why memo G labels the server-path claim STRONGLY SUPPORTED rather than VERIFIED; the direction of the finding does not depend on it. Attempt fails.
3. "The code comments say no read path exists for histograms in range queries, so this is a documented non-feature." Checked: the comments are stale and self-contradicting: histogram.rs:13-24 claims native histogram samples cannot reach the evaluator while the corpus header records that they do, and functions/mod.rs:415-418 claims no read path exists while the instant arm of the same registration uses that exact path. Stale comments masking a silent-wrong-data family are evidence of the defect, not a defense. Attempt fails.

Resolution: P1 stands (P0-equivalent for a native-histogram shop, per memo G's severity note), consolidated with R4/R5 as one family with one fix shape: make every reducer and operator histogram-aware or refuse typed, as the subquery guard already does; add (construct, input-type) rows to the difftest corpus so the conformance gate can see the axis. The endpoint asymmetry (instant correct, range empty for the same query) is the strongest single piece of evidence that this is an omission, not a decision.

## R8. Memo H finding P1-1: the alerting pipeline exports no metrics; its silent failure is undetectable except by log reading or missed pages

Falsification attempts:

1. "The failures are logged at warn; log-based alerting covers it." Rejected as a defense of the default posture: the repo's own operational model (memo H's inventory) gives every other correctness-relevant background loop a failure counter with a documented alert rule (maintenance stalls, tenant discovery, admission reconciliation, durable-auth refresh, metadata sink, scrub). The alerting engine is the one exception, verified by exhaustive grep over the single metrics renderer: zero `ravel_alert_*` names (re-verified by the chair on this host: grep count 0), and the in-memory AlertEvalReport is exported nowhere.
2. "Readiness or the store probe would surface the underlying store fault." Checked: the store probe reads `sys/tenancy` only; a per-prefix read failure on one tenant's `sys/alerts` history (the concrete scenario: a credential scoping error after per-tier rotation) leaves the probe green and `/readyz` up while every evaluation tick logs and skips. Attempt fails.
3. "Alerting is not reachable through the operator anyway, so the blast radius is narrow." Partially sustained as a precondition (the CRD cannot configure alerting, so only flag-configured deployments are exposed) and rejected as mitigation: for any deployment that uses alerting, the failed mechanism is the one that reports every other failure, which is what makes silence here worse than silence elsewhere.

Resolution: P1 stands. The fix is small and shaped like the repo's own conventions: render an AlertEvalReport-backed metric family and add the two alert rules to the operations guide. Until then, the documented workaround (a synthetic canary rule that fires periodically, paging on its silence) belongs in any adopter's runbook.

## R9. Memo H finding P1-2: no supported rolling upgrade or rollback across a data-format bump; readers accept exactly one RSEG version

Falsification attempts:

1. "The ADR-0066 machinery (migrate command, format floors, audit-versions, re-encode primitive) already enables safe upgrades." Checked: the machinery exists but the reader window does not: `SUPPORTED_VERSIONS = SupportedVersions::single(VERSION_V7)` (format.rs:129, re-verified on this host), and ADR-0092:244 states plainly that `maintain migrate` cannot rewrite v6 objects because a single-version reader cannot open its own migration inputs. The machinery has never carried a live bump. Attempt fails.
2. "Format bumps are rare; this is hypothetical." Checked: RSEG moved v5 to v6 to v7 across recent releases, RLOG and RSPAN moved similarly (section 12); the next bump is the expected case, not a tail risk, and the project's own ADRs treat it as imminent enough to have designed the successor policy. Attempt fails.
3. "Failures are typed and fail-closed, so no data is lost and the severity is overstated." Rejected: unreadable converts to deleted on schedule, because retention expiry evaluates without reading data objects (consistency-model.md's own expiry description), so v6 objects under a v7 binary are first unavailable and then permanently destroyed by a correctly functioning retention pass. Fail-closed reads do not stop the deletion path.

Resolution: P1 stands as an operational posture finding: every format-bump release is a non-rollbackable maintenance event, and an upgrade with data anyone cares about requires a Tier 1 bucket snapshot first. The exit criterion is the ADR-0066 N/N-1 window actually in force (a two-version SUPPORTED_VERSIONS and one exercised migration), not more documentation. See R10 for the governance half.

## R10. Memo L finding 1 (P1): the format-lifecycle documents contradict the shipped 0.10.0 reader deletion; the record says the single-version policy had already expired

Falsification attempts:

1. "0.9.0 was not really the 'first public release' in the ADR's sense; the policy trigger has not fired." Checked both ways: CHANGELOG.md:182 says the exact words "First public release" for 0.9.0 (re-verified on this host), and ADR-0027's status line says "superseded at first public release by ADR-0066"; nothing anywhere defines the trigger as a 1.0 milestone. Against that, ADR-0092:7 invokes "the pre-release regime of ADR-0027" and both format docs still say pre-release, so the project evidently regards the trigger as unfired. The attempt neither succeeds nor fails cleanly: the record contradicts itself, and either reading leaves one set of documents wrong. This unresolved internal ambiguity is preserved per charter; what is not ambiguous is that an adopter reading the ADRs and format docs would form the opposite belief about upgrade safety from what the 0.10.0 binary does.
2. "No real deployment holds v6 data, so nobody can be harmed." Checked: ADR-0092:249 itself calls whether any store holds v6 "the first question the epic asks", so the project could not answer it either; unverifiable from the checkout and irrelevant to the drift finding, which is about what the documents promise adopters going forward. Attempt fails.
3. "The changelog disclosed the deletion plainly, so the docs are honest in aggregate." Partially sustained: the disclosure is real and prominent, which is why this is a documentation-governance finding rather than a hidden data-loss bug. Rejected as full mitigation: the changelog is a release announcement; the ADRs and format documents are the artifacts that exist to answer "is my stored data safe across upgrades", and they answer it wrong in the safe-sounding direction.

Resolution: P1 stands, scoped as documentation governance with a data-loss consequence chain (unreadable, then retention-deleted) rather than a code defect. Same root facts as R9; one fix closes both: either ship the N/N-1 window before the next bump and mark ADR-0027 superseded in the ADR index, or amend ADR-0066 and the format docs to state that the single-version regime remains in force and every upgrade across a bump is destructive without a bucket snapshot. The intolerable state is the current one, where the two halves of the record disagree.

## R11. Memo I finding 1 (P1): request-dominated economics at defaults with a structural strict-mode floor

Falsification attempts:

1. "The dollar figures are derived, not measured; the real bill could be far lower." Checked: the per-stream formulas were verified against the shard, reconcile, sweep, and resolve code paths at file:line; the parameters are shipped defaults read from code; and ADR-0076, an internal analysis this review did not author, independently models 97 percent of the bill as requests and lands within the same order of magnitude at the same workload point. The absolute dollars scale with the assumed workload mix (stated inline in memo I); the structure (requests dominate storage by 30-100x, cost scales with object count not bytes) is corroborated in-repo. Attempt fails against the structure, succeeds only against decimal precision, which the memo never claimed.
2. "The shipped levers (replica affinity, per-tenant resharding, buffered mode) fix it." Checked: the levers are real and reduce the Medium workload roughly 3x, but the floors survive them: the 3-second strict-visibility ceiling is a compiled constant enforced at startup (config.rs:1023, 2025, re-verified on this host), capping the cadence lever at about 2.5 s; and cross-tenant coalescing, the only lever that would break the per-tenant floor, is explicitly rejected on isolation grounds in ADR-0076. About $10/month per strict (tenant, signal) remains at minimum configuration. Attempt fails.
3. "This is a designed trade, not a defect; the repo documents it candidly." Sustained in part: it is a designed boundary, ADR-0076 is unusually candid, and nothing here is hidden. The resolution reflects that: this is an adoption-scoping finding, not a bug. It is P1 because it is a hard economic blocker for a workload shape (many-tenant strict-mode SaaS, free tiers, per-seat pricing) that an adopter could reasonably assume the multi-tenant feature set was built for, and nothing in the adopter-facing docs states the floor; the cost guide's formula also omits the background request streams entirely (admission reconcile, orphan-GC LISTs, per-resolve LISTs), which is the attached P2 doc finding.

Resolution: P1 stands, scoped: not a correctness or availability defect, but a structural economic boundary that must be in the adoption decision. Deployments with few tenants or buffered-acceptable signals are unaffected in kind, only in degree.

## R12. Memo I finding 2 (conditional P1): a multi-hour compaction stall converts to read unavailability (typed 422s) for busy tenants on cold queries

Falsification attempts:

1. "Caches absorb the open-hour reads, so the budget never binds." Checked: the per-tenant record cache defaults to 10,000 entries while a busy tenant's unsealed window holds roughly 14,400 commit records at defaults (2 replicas x 4 shards x 2 h at 2 s cadence), so the busiest tenants thrash it; caches are per-process RAM only, so every query node pays separately, and the resolve LISTs are structurally uncacheable. Attempt fails for exactly the busy-tenant cold-query case the finding names.
2. "The budget is a flag; an operator can raise --max-s3-requests and escape." Sustained as workaround, rejected as falsification: the default derived budget (about 15,800 at 4 shards, 2 s) covers roughly two busy open shard-hours, so the default behavior under a stall is fleet-wide 422s for that tenant's cold queries, and the operator discovers the flag during the incident. The failure is typed and visible, never silently partial, which is why this stays conditional-P1 rather than higher.
3. "Multi-hour compaction stalls are rare." Rejected: the repo ships stall gauges, ownership metrics, and runbook alert rules for exactly this condition (memo H), which is evidence the project expects stalls; and the catch-up compaction that follows a long stall is the same operation that can trigger the R2 fold-window defect, coupling this finding to a second one.

Resolution: conditional P1 stands (preconditions: busy tenant, stall of several hours, cold caches). The recommended fix (scale the budget by observed unsealed-hour count, or admit early L1 parts) and the proof test (maintain paused four hours under 2 s cadence, queries must still answer) are as memo I stated.

## R13. Memo J finding P1-1: no credible performance envelope; the suite cannot detect a performance regression; the one published number quotes a forbidden control arm

Falsification attempts:

1. "Refusing to publish non-reproducible numbers is the right discipline, so the absence is a virtue, not a finding." Sustained for the discipline, rejected for the conclusion: the charter is explicit that a project with no credible performance envelope cannot receive full production-readiness marks regardless of correctness, and the repo's own ADR-0070 concedes the operative consequence ("nothing gates performance at all: a past eager-decode regression merged silently"). The virtue and the gap coexist; the gap is the finding.
2. "The 2.99x CHANGELOG figure is accurate as measured, so there is no misquote." Checked on this host: both figures (26.5167 and 8.8767 bytes per sample) come from the `random_float(ctrl)` arm of the golden byte-count file, and ADR-0092's own amendment classifies that arm as a worst-case control, not the representative cost (representative arms land at 8-10x). The arithmetic is correct; the methodology is the one the ADR forbids, and the direction happens to be conservative (the true improvement is understated). A correct number produced by a forbidden method is still a process defect: next time the direction may flip. Attempt fails.
3. "The weekly bench-s3 lane is the real-S3 envelope." Checked: it runs a 10-second workload at a 500 ms flush cadence against the 2 s production default, skips green when credentials are absent, has no baseline or threshold, and its artifact expires after 90 days. It is a smoke test that the harness still runs, not an envelope. Attempt fails.

Resolution: P1 stands, and it corroborates memo I's independent same-conclusion finding from the modeling side. The exit criterion is ADR-0070 tier B as already designed in-repo (committed baselines, bench_compare, an advisory PR comparison) plus one recorded bench-s3 run at production cadence; the proof is a seeded regression on a branch turning the gate red.

## R14. Memo J finding P1-2: operational-resilience evidence is claimed but does not exist; the chaos lane is unrunnable dead code; no test kills a maintain worker; zero soak evidence

Falsification attempts:

1. "The chaos scripts pass their --check self-validation, so they work." Checked: --check validates script structure and dependency presence only; all four defects sit downstream of it. Two of the four were re-verified by the chair on this host: the metric parser selects samples by exact name match (`awk '$1 == n'`, lib.sh:398) while every metric it reads renders with labels (`ravel_ingest_flushes_by_size_total{mode=...,signal=...}`, metrics.rs:704-708), so every read returns empty; and scenario 1 queries `chaos_requests_total` while the fixture it drives emits `demo_requests_total` (kill-ingest-flush.sh:41 vs gen_otlp_fixture.rs:45). Memo J verified the other two (tokens regex-matched as integers; scenario-2 load generated but never sent). The lane cannot ever have passed. Attempt fails, and explains why memo H's earlier structural check (--check exit 0) was not evidence of runnability.
2. "ADR-0077's Accepted status covers the posture design, not executed evidence, and the DR guide honestly says unrehearsed." Partially sustained on intent: the DR guide's empty rehearsal table is honest, and this review credits it. Rejected on substance: the ADR describes the scenarios' oracles as pinned, and a reader of Accepted ADRs reasonably concludes the tooling works; "never run and cannot run" is materially worse than "not yet run", and only code reading reveals which one this is.
3. "The CI kill-and-recover demo covers process death." Checked: it is real and well-asserted (SIGKILL, exit-137 verification, per-run metric suffix, explicit DATA LOSS verdict on an unsatisfiable token), and it covers a single-container all-mode stack only. Nothing anywhere kills a maintain worker mid-compaction and asserts sibling takeover; the takeover math is unit-tested as a pure function. The strongest durability property (strict-ack) has process-kill evidence; the maintenance ownership protocol does not. Attempt narrows the finding, does not falsify it.

Resolution: P1 stands. The gap it hides is bounded by the strength of the in-process crash matrices (which is why the shipped-defect probability is moderate rather than high), but RPO/RTO remain unmeasured, the DR runbook has never been executed, and the six-item chaos fix list plus one recorded run wired into the nightly k8s lane is the concrete exit criterion.
