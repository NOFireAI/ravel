# Agent H memo: SRE, operability, disaster recovery (feeds report sections 17 and 18)

## Verdict

Ravel is operationally serious and unusually honest for its stage: readiness with real hysteresis, fail-closed startup gates, drained shutdown with tests, a leased multi-worker maintenance protocol whose liveness and stalls are exported as metrics, a bounded-cardinality metrics surface enforced by the type system, runbooks that document their own blind spots, and a DR posture that refuses to publish RPO/RTO numbers it has not measured. An experienced operator could own the process-level failure modes at 03:00 from the operations guide alone. The material gaps are day-2 and platform-level, not process-level: the alerting pipeline is the one correctness-relevant background mechanism with no metrics (log-only failure visibility); the Kubernetes operator's CRD cannot express a large fraction of the production flag surface and renders no PodDisruptionBudget, anti-affinity, topology spread, or securityContext; format-bump upgrades are still the pre-release wipe posture (single supported RSEG version, v6 reader deleted when v7 landed), so rolling a data-format upgrade or rolling back after new-format objects exist is unsupported today; and disaster recovery is entirely operator-owned bucket controls with a well-written but never-rehearsed restore runbook whose RPO/RTO fields honestly read "unmeasured". Nothing I found is a credible P0. The system's default posture (Tier 0, unversioned bucket) makes bucket loss total loss, and the docs say so plainly.

## Evidence

### Health, readiness, hysteresis, shutdown

Finding: liveness and readiness are correctly separated, readiness reflects store reachability with asymmetric hysteresis, and shutdown drains ingest buffers. VERIFIED (code plus in-tree tests; the panel host reports the full workspace suite, roughly 5400 tests, green; I did not rerun broad suites).

- `/healthz` is stateless liveness, `/readyz` is startup latch AND background store reachability: `services/ravel-server/src/health.rs:53-114` (one-way latch, `is_ready()` at L81-83 ANDs `store_probe::store_reachable()`); Prometheus spellings `/-/healthy` `/-/ready` route to the same handlers (L89-99). Test `readiness_starts_not_ready_flips_once_and_never_reverts` health.rs:121-136.
- Store probe: one background GET of `sys/tenancy` per `--store-probe-interval` (default 30 s, jittered), K=4 consecutive failures to go unready, one success to recover: `services/ravel-server/src/store_probe.rs:50,54,106-114,129-143`. `NotFound` counts as reachable (L133-134), so an unbootstrapped bucket cannot flap readiness. K is a constant, deliberately not a flag, so an operator cannot reintroduce single-blip mass ejection (L43-49). Test `hysteresis_needs_k_failures_and_one_success_recovers` store_probe.rs:215-245. Exported as `ravel_store_reachable` gauge and `ravel_store_probe_failures_total` counter (metrics.rs:1406-1432) so a metrics-only setup sees the outage. Liveness deliberately independent, so a store outage cannot trigger a restart storm (health.rs:50-52).
- Shutdown: SIGTERM/ctrl-c handled (`services/ravel-server/src/main.rs:489-533`), then `Running::shutdown` (`services/ravel-server/src/lib.rs:467-542`) stops all listeners, drains and joins every ingest shard actor (metrics, logs, spans), then stops background tasks, metadata sink last with a final flush. Drain tests exist per pipeline: `crates/ravel-ingest/src/log_shard.rs:1204` (`shutdown_drains_buffered_records`), `:1532` (`shutdown_joins_inflight_flush_before_returning`), `span_shard.rs:1116,1372`. The shard drain awaits flush acks with no internal deadline (`crates/ravel-ingest/src/router.rs:459-472`); termination is bounded only by the flush retry budget and Kubernetes' grace period.
- One caveat in the drain path: if any `Arc<IngestRouter>` reference is still held at shutdown, `Arc::try_unwrap` fails and the process logs "shard actors not drained" and skips the drain (lib.rs:492-501). Strict-mode acked data is already durable regardless (see below); only the buffered-mode window is at risk, which is that mode's documented contract. IMPLEMENTED WEAKLY VERIFIED (warn-and-skip path; I found no test that exercises the leaked-reference branch).
- Ack semantics that make crash/kill tolerable: strict mode acks only after data PUT, commit PUT, and marker PUT (docs/consistency-model.md:9-21,184, crash matrix at L335-342); buffered mode is opt-in and loses at most the flush window. DOCUMENTED CLAIM for the matrix itself; the panel-provided 100-seed simulation run and the crash-path tests in ravel-ingest support it, and durability is another agent's charter.
- `ravel-ingest-router` (the native affinity router) has its own `/healthz` `/readyz`, and readiness is gated on the first EndpointSlice sync so a rolling deploy never serves from an empty subset: `services/ravel-ingest-router/src/proxy.rs:23-43`, tests `services/ravel-ingest-router/src/tests.rs:350-356,373-401`. VERIFIED (tests in-tree, suite green).

### Startup gates and configuration validation

Finding: startup is fail-closed on every durable-contract precondition, before any listener binds. STRONGLY SUPPORTED (code read; gates covered by crate tests I did not rerun).

- Qualification gate: a production store refuses to start unless `sys/qualification` exists at a current suite version; there is deliberately no fresh-bucket bypass (`services/ravel-server/src/qualification.rs:1-67`). Every bootstrap path I checked runs it: `scripts/kind-up.sh:202-247` (a Job), `scripts/demo.sh:88-90`, `deploy/docker-compose/ravel.yml:49-77` (one-shot `qualify` service). Operations guide documents the required first-deployment order (docs/guides/operations.md:1122-1145).
- Tenant-hash scheme pinning, static shard-count provisioning validation, durable GC-config validation, retention floor validation, admission-limits file validation, alert rules and sink validation, OIDC JWKS plaintext refusal: `services/ravel-server/src/main.rs:103-397`. A wrong deployment key or a disagreeing shard count is a failed deploy, not a silent split namespace (main.rs:109-121,159-178).
- Bucket-protection gate honesty: `--require-bucket-protection` (rendered unconditionally by the operator, reconcile.rs:342-360) can only fail closed on `Disabled`/ALARM probes, and every backend reachable through `ObjectStoreBackend` today reports `Unknown`, which logs a warning and sets the `ravel_bucket_protection_unknown` gauge instead of blocking (`services/ravel-server/src/bucket_protection.rs:10-19,56-71`). So in practice this gate is advisory on real S3. The limitation is stated in the module docs and the gauge exists to alarm on. CONTRADICTED only in the weak sense that the flag name promises more than production backends can deliver; the code and docs disclose it.
- Config knobs that parse but do not enforce are warned about loudly by name (per-tenant `max_bytes_scanned` overrides, alert rules in a non-evaluating mode): main.rs:308-379. This "looks configured, is actually inert" discipline is exactly what an operator needs.

### Kubernetes operator and manifests

Finding: the operator is a competent, idempotent, well-tested renderer of a deliberately narrow surface; the gaps are scheduling/disruption hardening and CRD expressiveness. STRONGLY SUPPORTED (code plus in-tree unit tests over rendered objects; kind/kubectl are not installed on this host, so live-cluster behavior is NOT ASSESSED, environmental).

- CRD: CEL immutability on `shards` (`self == oldSelf`), minimum-1 bounds on shards/replicas, cross-field CEL guards for affinity/exposure combinations, all injected post-hoc and unit-tested without an API server (`services/ravel-operator/src/crd.rs:754-1064`, tests :1071-1166 and onward). The committed `deploy/k8s/operator/crd.yaml` carries the rules (3 `x-kubernetes-validations` blocks; grep confirmed, line 443-444 carries the shards rule).
- Reconciliation: server-side apply per child, owner references on every child so CR deletion garbage-collects cleanly (no finalizer needed; bucket data intentionally survives), apply-then-sweep for optional objects (ingresses, routes, router RBAC), maintain Deployment deleted when disabled, requeue on a fixed resync, Degraded status written on any failure so `kubectl wait` fails with a reason instead of timing out (`services/ravel-operator/src/controller.rs:863-1209,1471-1474`). Status carries `Available`/`Degraded` plus per-tier readyReplicas; `Progressing` is admitted as not implemented (docs/guides/kubernetes.md:288-292).
- Secret handling: S3 credentials via `valueFrom.secretKeyRef` env, tenant tokens via `$(VAR)` kubelet expansion so values never land in the Pod spec (though they do appear in process argv, admitted at kubernetes.md:212-217); per-tier credential overrides (ADR-0055) with a per-Deployment secrets checksum annotation that rolls exactly the tiers consuming a rotated Secret (`services/ravel-operator/src/reconcile.rs:84-196,222-311`). Deployment-key rotation rolls all tiers (RenderCtx, reconcile.rs:126-131). The `=`-in-token parsing hazard is documented on the CRD field itself (crd.rs:60-66).
- Probes: liveness `/healthz`, readiness `/readyz`, sane thresholds, on every tier including maintain (reconcile.rs:425-458, tests :2188-2208).
- What the operator does NOT render (grep over reconcile.rs found no occurrence): PodDisruptionBudget, pod anti-affinity, topologySpreadConstraints, securityContext, terminationGracePeriodSeconds, automountServiceAccountToken, priorityClass, ServiceAccount for server pods. The distroless `:nonroot` images (Dockerfile:74,97,115) mitigate the missing securityContext at the image layer only. NOT IMPLEMENTED.
- RBAC: mostly least-privilege with an explicit rationale per rule (deploy/k8s/operator/rbac.yaml:1-29), but `secrets: get` is granted in a ClusterRole with no resourceNames or namespace scoping (rbac.yaml:75-77): a compromised operator pod can read any Secret in the cluster by name. Operator runs single-replica Recreate with no leader election, declared intentional (deploy/k8s/operator/operator.yaml:24-28).
- The operator itself performs object-store writes each cycle when configured: `sys/auth` reconciliation (best-effort, bounded CAS retries, never blocks child reconciliation; empty Secret read never mass-revokes) and `shardOverrides` resharding via the ADR-0052 `append_generation` mechanism with an enforced 2 h lead floor (controller.rs:932-974, crd.rs:627-654). STRONGLY SUPPORTED from code and doc (kubernetes.md:219-258).
- CRD expressiveness gap: no field or passthrough exists for `--limits-file` (admission limits), alert rules/sinks, the ADR-0088 query-budget flags, cache configuration, `--store-probe-interval`, distributed query, OIDC/mTLS, per-tenant KMS routing, `--metrics-tenant-labels`, indexed fields, or typed attribute columns, and there is no extraArgs/env escape hatch (full spec surface: crd.rs:35-111). An operator-managed production cluster runs shipped defaults for admission control and cannot use alerting at all. NOT IMPLEMENTED (verified by reading the whole spec struct set).

### Upgrades and rollback

Finding: within a format version, rolling upgrades are well-supported by statelessness and the maintenance ownership protocol; across a data-format bump, upgrade today is the documented pre-release wipe posture, and rollback after new-format objects exist is unsupported (fail-closed, not corrupting).

- All three tiers roll with RollingUpdate, including maintain: ADR-0065's heartbeat/rendezvous ownership makes multi-replica and mixed old/new maintain workers safe, superseding ADR-0034's Recreate guidance (reconcile.rs:635-645, tests :2004-2023,2109-2133). Secrets rotation and spec changes roll pods through the checksum annotation. Old-query/new-ingest and new-query/old-ingest at the same format version share frozen contracts (proto field numbers frozen, key layout unversioned by design). STRONGLY SUPPORTED.
- Format bumps: RSEG readers accept exactly one version today, `SUPPORTED_VERSIONS = SupportedVersions::single(VERSION_V7)` (`crates/ravel-segment/src/format.rs:129`), typed refusal `SegmentError::UnsupportedVersion` (`reader.rs:87-88`). ADR-0092 deleted v6 read and write support in the same change that introduced v7: "Existing v6 objects become unreadable ... wiped or re-ingested, which decision 6 already accepts" and states plainly that `maintain migrate` cannot rewrite v6 under this policy (docs/adrs/0092:238-248). So: a rolling deploy across that bump would have had old queriers fail typed on new objects, and rollback after new objects were written leaves the old binary unable to read them. Fail-closed, never silent misreads. CONTRADICTED only against a production-upgrade expectation; as a pre-release policy it is explicit (ADR-0027 decisions 6-7).
- The machinery for real production upgrades exists and is partially exercised: readers-before-writers rollout order documented as a runbook (docs/guides/operations.md:1684-1705), `ravel-cli maintain migrate` with durable cursor, budget, and verify-then-raise-floor semantics (operations.md:1653-1682), `maintain audit-versions`, per-(tenant, signal) format floors (ADR-0066 decisions 1-3), and the re-encode primitive (`reencode_run_to_current_version`, cited by ADR-0092 at build.rs:537-594). But the N/N-1 reader window is not in effect in this tree, so the machinery has not yet carried a live bump. IMPLEMENTED WEAKLY VERIFIED for the machinery; NOT IMPLEMENTED for a rolling format upgrade today.
- Catalog HEAD forward-compatibility under mixed versions: the fold distinguishes `UnsupportedVersion` from `Corrupt` and never CAS-overwrites a newer-format HEAD (`crates/ravel-catalog/src/fold.rs:171-203,856-858`), closing the rolling-upgrade clobber hazard ADR-0066 found. VERIFIED (typed state plus the suite-green run).
- CRD/operator upgrades: `v1alpha1` with an explicit no-compatibility-promise statement (kubernetes.md:162-164).

### Maintenance, GC, and background-mechanism observability

Finding: the maintenance system is the best-observed part of the platform; the alerting engine is the worst.

- Leased distributed maintenance (ADR-0065): per-process heartbeats under `sys/maintain/workers/`, rendezvous partition of `(tenant, signal, shard)` units, per-unit stall tracking, memo warm starts. The heartbeat runs concurrently with discovery specifically because a long discovery pass once starved the heartbeat past the liveness window; the fix and its reasoning are in the code (`services/ravel-server/src/maintain.rs:623-646,246-341`). Exported: `ravel_maintain_workers_live`, `units_owned`, `units_stalled`, `memo_warm_start_units_total`, `full_sweep_passes_total`, merge-memory peaks (metrics list confirmed by grep over metrics.rs; operations.md:1725-1761 documents each with alert rules `workers_live == 0` and `units_stalled > 0 for 30m`). VERIFIED (code, metrics, documented rules; chaos script structure check passed, below).
- Tenant discovery: a failed `LIST t/` skips the whole cycle and increments `ravel_maintain_tenant_discovery_failures_total`, never misread as "no tenants"; `tenants_maintained < tenants_discovered` is a documented alert (operations.md:1865-1866). VERIFIED.
- GC safety: mass-orphan circuit breaker with trip counter and withheld/present gauges, and a runbook that explicitly documents that the breaker is not self-clearing (dilution, partial restoration), its floor and ratio blind spots, and the absence of cross-shard aggregation (operations.md:1893-1965). This level of self-criticism in an operator doc is rare and load-bearing. The `orphans_present` gauge exists precisely to close the small-scale-loss blind spot (ADR-0058 decision 1). VERIFIED against metrics.rs and the documented rules.
- At-rest scrubber (ADR-0059): `ravel_scrub_*` counters plus a cursor-position gauge, so silent corruption and seal divergence have a detection channel. VERIFIED (metric names in metrics.rs, ops guide section at operations.md:534-613).
- Catalog fold: failures are logged only (`services/ravel-server/src/fold.rs:211,291`); there is no `ravel_fold_*` metric family and no fold-watermark-age gauge (grep over the full metric name set). A silently stopped fold never corrupts results (fold is a cost optimization) but degrades query cost toward the >10,000-commits-per-bucket listing wall the known-limitations section names (operations.md:2033-2040). NOT IMPLEMENTED (fold observability).
- Alerting engine (ADR-0043): rule-evaluation failures, history-read failures, lease failures, and sink delivery failures are tracked in an in-memory `AlertEvalReport` and logged at warn (`services/ravel-server/src/alerting.rs:459-530`), but no `ravel_alert_*` family exists at `/metrics` (grep over metrics.rs: zero hits for `AlertEvalReport` or an alert family). A wedged alert pipeline, the mechanism operators use to notice everything else, is itself detectable only by log inspection or by the silence of expected notifications. NOT IMPLEMENTED (alerting observability); the evaluation logic itself is out of my charter.
- Admission reconciliation, durable-auth refresh, metadata sink: each has failure counters (`ravel_admission_reconciliation_failures_total`, `ravel_durable_auth_refresh_failures_total`, `ravel_ingest_metadata_flush_dropped_total`). VERIFIED via metrics.rs.

### Disaster recovery and platform-loss scenarios

Finding: DR is a defined, honest, operator-owned posture with real reconciliation tooling, but it is unrehearsed and the default tier is "bucket loss is total loss".

- Posture: no in-product backup, export, or failover; three tiers (Tier 0 default = unversioned bucket, total loss on bucket loss; Tier 1 = versioning + lifecycle + cross-region cross-account replication with `DeleteMarkerReplication` mandatory for erasure-obligated deployments; Tier 2 = plus Object Lock), each with its erasure-bound cost disclosed (docs/guides/disaster-recovery.md:10-116). The replica is a restore source, never a live failover target, because replication breaks commit-then-visible ordering (DR guide:152-162). DOCUMENTED CLAIM, consistent with the store contract.
- Restore tooling referenced by the runbook exists in the CLI: `commit reconstruct` (`services/ravel-cli/src/reconstruct.rs`, dispatched main.rs:775), `maintain verify-custody` (main.rs:869), `store qualify` (main.rs:903, qualify.rs), `catalog verify` (catalog.rs). The stop-maintenance-first discipline is a real runbook with the reason (the sweeper races the restore) and the honest limitation that no per-tenant maintenance exclusion exists once a tenant has a config record, so repair means stopping maintenance for everyone (operations.md:1967-2020). VERIFIED that the tools exist and are wired; their restore behavior itself I did not exercise against a store.
- RPO/RTO: defined (RPO = data-object replication lag plus quarantined dangling records, 15 min ceiling only with RTC; RTO = freeze-to-verified-resume) and deliberately published as "unmeasured" until a rehearsal record exists (DR guide:218-254). The chaos-evidence lane exists: `scripts/chaos/kill-ingest-flush.sh` and `kill-maintain-worker.sh` with pinned oracles (sibling takeover within 3H+tick, conservation gate, no partial-output leak) and a release-blocking exit-code contract; both pass their `--check` structural validation on this host (exit 0), but no real run is recorded and the rehearsal table reads "unrehearsed". IMPLEMENTED WEAKLY VERIFIED (scripts exist and self-validate; no recorded execution).
- Loss-scenario implications, from evidence:
  - One pod / one node: strict-acked data durable (consistency model crash matrix); buffered window lost by contract; maintain units re-partition within the ADR-0065 liveness bound; no local state to recover. STRONGLY SUPPORTED.
  - Whole Kubernetes cluster: redeploy manifests plus CR; all durable state is in the bucket, with two exceptions that must survive outside the cluster: the deployment key (tier-0 state; a keyed bucket refuses startup under a wrong key, and losing the key makes every tenant prefix unattributable, operations.md:2054-2086) and the tenant-token/credential Secrets. The DR restore procedure (steps 1-6) never mentions carrying the deployment key or tenant-KMS config to the restore environment. Doc gap.
  - Object-store connectivity loss: ingest fails 503/UNAVAILABLE (strict), buffer budget sheds before OOM (ADR-0069), readiness drops fleet-wide after roughly 2 minutes of hysteresis and recovers on the first good probe; retry classification is a pinned conformance contract (`crates/ravel-object-store/src/conformance.rs:1084-1223`). VERIFIED.
  - KMS unavailability (per-tenant SSE-KMS): scoped to the affected tenant's data-plane calls; key deletion is the crypto-erasure path by design (ADR-0062/0064). Restore under a different `ReplicaKmsKeyID` requires re-pointing tenant KMS config; not covered by the DR runbook. DOCUMENTED CLAIM plus a doc gap.
  - AZ loss: S3 is regionally durable; compute reschedules, but the operator renders no anti-affinity or topology spread, so replica placement is unmanaged. Region loss: Tier 1 restore path or total outage at Tier 0.
  - Accidental delete: layered mitigations that are real: per-role IAM with delete granted only to Maintain over four prefixes and an explicit `DenyDeleteProtected` on all roles including Admin (deploy/iam/*.json, verified by parsing all four policies; Admin has no delete grant at all), the mass-orphan breaker plus `orphans_present` alert for record loss, `commit reconstruct` for record-side loss, and Tier 1 versioning for object-side loss. STRONGLY SUPPORTED.
  - Credentials loss/rotation: per-tier Secret rotation rolls exactly the consuming tier via checksum annotation; `assert`-style startup refusals catch wrong keys.

## Failure scenarios (constructed)

1. Alert pipeline silently wedged (supports P1 finding 1): a tenant's `sys/alerts` history prefix becomes unreadable (credential scoping error after a per-tier rotation). Every `run_tick` logs "could not read alert history; skipping tick" (alerting.rs:466-470) and returns. No metric moves; `/readyz` stays green (store probe reads `sys/tenancy`, which is fine); notifications simply stop. The operator's first signal is the absence of expected alerts during the next real incident. Probability: moderate (any sustained per-prefix read failure or sink outage triggers it); blast radius: the deployment's entire alerting function.
2. Node drain takes ingest down: with no PDB and no anti-affinity, both gateway replicas can sit on one node; a routine drain evicts both simultaneously. Strict-acked data is safe; availability drops to zero for ingest and query API until reschedule, and every buffered-mode window on both pods is lost at once. Voluntary disruption, so a PDB would have prevented it.
3. Rollback after a future format bump: fleet writes v8 objects for an hour, a regression forces rollback to the v7-only binary; every query touching a v8 object fails typed `UnsupportedVersion`, compaction cannot open v8 inputs, and the only paths forward are roll forward again or wait out retention. No corruption, but no supported rollback either.
4. Operator-managed cluster under tenant abuse: no CRD field reaches `--limits-file`, so shipped default admission limits apply; a hostile tenant's series-cap pressure can only be mitigated by abandoning the operator or rebuilding images. Documented shipped defaults bound the damage (operations.md:110-142), but per-tenant tuning is unreachable.
5. DR restore surprise: an operator runs the Tier 1 restore runbook to a fresh account, forgets the deployment key exists (it lives in a K8s Secret in the dead cluster, and the runbook never names it); every server refuses startup against the restored keyed bucket with a fingerprint mismatch. Recoverable only if the key survived somewhere else; the runbook should say so at step 5.

- Whether `reconcile_shard_overrides` is fully idempotent against a flapping operator (it re-runs every cycle; the no-op-on-equal-count claim is documented at kubernetes.md:175 and crd.rs but I did not trace the append-generation guard end to end).

## Severity-ranked findings

**P1-1. The alerting pipeline is the one correctness-relevant background mechanism with no metrics; its silent failure is undetectable except by log-reading or by missed pages.**
- Scenario: failure scenario 1 above. Any sustained history-read failure, lease-acquisition failure, rule-evaluation failure, or sink-delivery failure reduces the deployment's alerting to nothing while every gauge an operator watches stays green.
- Evidence: `services/ravel-server/src/alerting.rs:459-530` (log-only handling, in-memory `AlertEvalReport`); zero `ravel_alert_*` names in the metric inventory (command 5); no export of the report (command 7). Contrast with every other background loop, which has a failure counter (metrics inventory).
- Blast radius: the entire notification function of the deployment; secondary blast radius is every other failure mode whose alert rides this pipeline.
- Probability/preconditions: moderate; requires alerting to be in use (`--alert-rules-file`, only reachable outside the K8s operator today) plus any sustained per-tenant store or sink fault.
- Workaround: log-based alerting on the four warn lines; synthetic canary rule that fires periodically and pages on silence.
- Fix: render an `AlertEvalReport`-backed family (`ravel_alert_ticks_total`, `rules_failed_total`, `history_unavailable_total`, `lease_unavailable_total`, `notifications_undelivered` gauge) under the existing mode-only label discipline; add rules to the operations guide.
- Proof test: unit test driving `run_tick` against a `FaultStore` that fails the history read, asserting the family renders nonzero; a second test asserting an undelivered-sink backlog is visible at `/metrics`.

**P1-2. No supported rolling upgrade or rollback across a data-format bump: readers accept exactly one RSEG version and the last bump (v6 to v7) shipped by deleting the old reader.**
- Scenario: failure scenario 3 above; equally, an operator upgrading a live fleet across the next bump with data they cannot wipe.
- Evidence: `crates/ravel-segment/src/format.rs:129` (`SupportedVersions::single(VERSION_V7)`), `reader.rs:87-88` (typed refusal); ADR-0092:238-248 ("existing v6 objects become unreadable ... wiped or re-ingested"); ADR-0066 defines the N/N-1 window, floors, and migrate machinery, and `maintain migrate`/`audit-versions` exist (operations.md:1653-1705), but the dual-reader window is not in effect in this tree.
- Blast radius: every query and compaction touching new-format objects after a rollback; availability of historical data during a botched rollout. Never silent corruption: refusals are typed.
- Probability/preconditions: certain at the next format bump if the single-version policy is still active when real deployments hold data worth keeping; the project's own ADRs say the policy expires at first public release.
- Workaround: treat format-bump releases as non-rollbackable maintenance events; snapshot the bucket (Tier 1 versioning) before upgrading.
- Fix: flip `SUPPORTED_VERSIONS` to the two-version window and ship the readers-before-writers procedure at the first post-release bump, exactly as ADR-0066 decision 1 specifies; publish the rollback stance in the operations guide.
- Proof test: the existing `SupportedVersions` unit tests extended to a `pair(V7, V8)` window; an integration test that writes v8, rolls a reader back to the v7+v8 window, and asserts reads succeed while a v7-only reader fails typed.

**P2-1. Operator CRD cannot express most of the production configuration surface, and there is no escape hatch.** Admission limits, alerting, ADR-0088 query budgets, cache, OIDC/mTLS, KMS routing, distributed query, probe interval: none reachable (crd.rs:35-111; no extraArgs). Fix: an `extraArgs`/`extraEnv` passthrough or first-class fields; test: render assertion that passthrough args land on each tier.

**P2-2. No PodDisruptionBudget, anti-affinity, topology spread, securityContext, or terminationGracePeriodSeconds on rendered Deployments** (grep over reconcile.rs; deployment builder at :465-530). Routine node drains can evict all replicas of a tier at once; buffered-window loss and total ingest unavailability follow. Fix: render a PDB (maxUnavailable 1) and default topologySpreadConstraints per tier, a restricted-profile securityContext, and a grace period sized to the flush retry budget; test: unit assertions on the rendered objects, like the existing strategy tests.

**P2-3. DR restore procedure omits the two secrets it cannot work without.** The deployment key (keyed buckets refuse startup without it; operations.md:2054-2086) and per-tenant KMS mappings are absent from the restore runbook's steps (disaster-recovery.md:164-216). Fix: add a step-0 "custody manifest" (deployment key, tenant KMS config, admin credential) to the runbook; proof: a rehearsal run that starts from only the replica bucket plus that manifest.

**P2-4. Catalog fold has no metrics (no failure counter, no watermark-age gauge); a stopped fold silently degrades query cost toward the documented 10k-commit listing wall** (fold.rs:211,291 log-only; operations.md:2033-2040). Fix: `ravel_fold_failures_total` and a watermark-lag gauge; test: render assertion after a failing fold tick.

**P3-1. Doc drift, three instances misdirecting operators:** kubernetes.md:301-320 (readyz/store-probe stale, contradicts shipped ADR-0050 section 7 behavior), kubernetes.md:270,277-280 plus the field table (maintain Recreate/one-replica stale versus ADR-0065 RollingUpdate; `maintain.replicas` missing), operations.md:1767 (`ravel_admission_active_streams` does not exist). Reported here per repo policy, not fixed.

**P3-2. Alert rules and dashboards ship as prose only.** No PrometheusRule YAML; the sole Grafana dashboard is a demo panel (`system_cpu_load_average_1m`). Fix: ship `deploy/prometheus/rules.yaml` generated from the operations-guide tables plus a Ravel-metrics dashboard.

**P3-3. Operator ClusterRole grants `secrets: get` cluster-wide with no resourceNames scoping** (rbac.yaml:75-77); server pods run under the default ServiceAccount with token automount. Hardening, not a breach path by itself.

**P3-4. `--require-bucket-protection` is advisory on every real backend** (always `Unknown` through `ObjectStoreBackend`; bucket_protection.rs:10-19). Disclosed via gauge and docs; still worth renaming or closing with a real probe ADR so the operator-rendered flag does not overpromise.

**P3-5. Tenant repair requires stopping all maintenance** (no durable per-tenant exclusion once a config record exists; operations.md:1980-1991). Documented honestly; a per-tenant maintenance hold object would remove a whole-fleet pause during single-tenant incidents.

## Confidence

- Health/readiness/hysteresis/shutdown semantics: high (code plus targeted in-tree tests plus the panel-reported green run).
- Operator rendering, CRD validation, secret handling: high for what is rendered (unit tests are thorough); medium for live-cluster behavior (NOT ASSESSED, environmental).
- Background-mechanism observability inventory (what has metrics and what does not): high (exhaustive metric-name grep against the single renderer).
- Upgrade/rollback posture: high on current single-version facts; medium on how smoothly the ADR-0066 machinery will carry the first real bump (never exercised end to end).
