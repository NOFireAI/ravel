# Agent K memo: build, release, and supply chain

## Verdict

The build, release, and supply-chain posture is unusually strong for a project of this maturity, and I found no P0 or P1 issue. VERIFIED on this checkout: a committed Cargo.lock (version 4) with `--locked` enforced in every CI and container build, an exact toolchain pin (1.97.1) used consistently by CI and the Dockerfile, crates.io as the only dependency source (no git, no path deps crossing the workspace boundary, zero wildcard requirements), cargo-deny 0.20.2 exiting 0 against the repo's own deny.toml with two ignored advisories whose written justifications I independently confirmed against the dependency graph, SHA-pinned third-party Actions in every PR-facing workflow, a tag-triggered release pipeline that gates on CI success, pushes by digest, attaches SBOM and max-mode provenance per platform, signs the assembled index with keyless cosign and then verifies its own signature, and distroless nonroot runtime images built by a pinned Rust builder. The residual findings are real but second-order: cargo-deny scans only the default-feature graph, leaving 29 lockfile packages (arrow-flight 58.4.0, the pprof/inferno profiling stack, and others) invisible to advisory and license checks; two scheduled workflows use floating-tag Actions, one of which holds live S3 credentials; base images and CI service containers are pinned by tag rather than digest; the "immutable" GHCR release tags are immutable by convention only; and ci.yml has no top-level least-privilege permissions block. All are P2 or P3 with straightforward fixes.

### The two ignored advisories, assessed per charter

RUSTSEC-2025-0141 (bincode 1.3.3, unmaintained). VERIFIED reachability claim: `cargo tree -i bincode@1.3.3` shows exactly the path deny.toml describes: bincode <- lrpar 0.13.10 <- lrlex <- promql-parser 0.10.0 <- ravel-promql <- ravel-query <- ravel-server. Runtime, not build-time only: lrpar deserializes build-baked grammar tables at parser construction inside the shipped binary. Attacker control: none; the only input bincode ever sees is the byte blob the build script embedded in the binary, so an attacker would need to control the build to control the input, at which point bincode is irrelevant. Exploitability: effectively nil in this configuration; "unmaintained" is a maintenance risk, not a live vulnerability. Upgrade path: none exists on bincode 1.x, and the dependency is upstream in promql-parser's parser generator; the deny.toml comment (deny.toml:8-19) is accurate on all these points and names the revisit condition. Acceptable ignore.

RUSTSEC-2024-0436 (paste 1.0.15, unmaintained). VERIFIED reachability claim: `cargo tree -i paste` shows paste (proc-macro) <- parquet 59.1.0 <- ravel-cli only. Build-time only: a proc-macro expands during compilation and contributes no code to the shipped binary. Attacker control: to exploit an unmaintained proc-macro an attacker must first compromise the crate on crates.io, which the lockfile hash pins against silently. Upgrade path: none upstream until parquet drops paste; the comment (deny.toml:21-31) correctly notes the suggested forks are not drop-in. Acceptable ignore.

Both justifications survived independent verification. This is better advisory hygiene than most production shops: the ignores are scoped to IDs, carry reachability analysis, and name revisit conditions.

### Container builds

VERIFIED, with one gap. The shipping Dockerfile is multi-stage: a `rust:1.97.1-bookworm` builder (Dockerfile:16) compiles with `--locked` and CARGO_BUILD_JOBS=2 (Dockerfile:46-50), splits debug info with objcopy (Dockerfile:63-68), and three runtime targets copy single binaries onto `gcr.io/distroless/cc-debian12:nonroot` (Dockerfile:74, 97, 115). ### Release workflow: provenance, signatures, SBOM, immutability

VERIFIED as designed; the workflow file is the evidence, not a run (I cannot observe GHCR or a release run from this checkout, so end-to-end execution is STRONGLY SUPPORTED by the file plus README documentation of the verify invocation, not observed). publish-images.yml triggers only on `v[0-9]+.[0-9]+.[0-9]+` tag pushes and manual dispatch (publish-images.yml:10-14). The gate job refuses to publish unless the workspace version equals the tag (lines 42-65, would have caught their own documented v0.9.0-as-0.1.0 incident) and unless a completed ci.yml run for the exact tagged SHA concluded success, failing closed on failure/absence/timeout (lines 76-121). Builds run on native runners per platform (no QEMU), push by digest with no tag (line 218), with `sbom: true` and `provenance: mode=max` on every platform image build (lines 219-220, 230-231, 241-242). Per-platform digests travel as artifacts (not matrix outputs, avoiding last-writer-wins, lines 244-296). The merge job assembles the index, applies tags, resolves the assembled index digest from the registry, cosign-signs that digest keyless (lines 441-466), then runs three verifications: signed digest equals the tag's current digest (lines 482-494), the index carries exactly linux/amd64+arm64 runnable entries (lines 503-519), and a full `cosign verify` against the documented certificate identity (lines 528-537). Least privilege is deliberately split: build jobs hold packages:write but no id-token; only merge holds id-token:write (lines 148-149, 346-349); the release job holds contents:write + id-token:write and no packages permission (lines 562-564). The release job re-verifies the images with cosign before extracting binaries from them by digest, ships one signed SHA256SUMS over all 10 assets with asserted counts (lines 747-774), and creates the Release with `--verify-tag` (lines 878-901).

Consumers who verify cosign signatures get authenticity; consumers who plain `docker pull` by tag (the compose file's pinned default, deploy/docker-compose/ravel.yml:53) do not. See finding K-3.

## Failure scenarios

1. Floating-tag Action compromise exfiltrates S3 credentials (K-2). Precondition: an attacker compromises the Swatinem/rust-cache repository or its v2 tag (or actions/checkout@v4, or upload-artifact@v4). bench-s3.yml runs weekly on schedule with `RAVEL_S3_ACCESS_KEY_ID`/`RAVEL_S3_SECRET_ACCESS_KEY` in job env (bench-s3.yml:80-81) and executes the tag-resolved action code on the same runner. The rust-cache action runs before the credentialed step but its post-step runs after, in the same job, with access to the process environment. Blast radius: the benchmark bucket's credentials, plus whatever those IAM credentials additionally permit (UNKNOWN from the repo). This is exactly the tj-actions/changed-files-class incident (March 2025) that SHA pinning exists to stop, and the repo already SHA-pins everywhere else, so this is drift, not policy absence.

2. Advisory blind spot behind `all-features = false` (K-1). Precondition: a RUSTSEC advisory lands against arrow-flight 58.x, pprof, inferno, nix, or any of the other 29 unscanned lockfile packages. The supply-chain CI job stays green, `make audit` stays green, and the flight-sql lane keeps compiling and running the affected code on every sql-area PR. Nothing surfaces until someone widens the graph or the feature ships in a release image and an external scanner catches it. The standing `license-exception-not-encountered` warning shows the config and the exceptions already disagree about which graph is being scanned.

3. Runtime base tag re-point (K-4). Precondition: compromise of gcr.io distroless publishing, or an upstream rebuild under the same :nonroot tag that introduces a regression or malicious layer. The next tag-push release builds on the new base with zero diff visible in the repo, and the pipeline then signs and attests the result: the signature proves this workflow built it, not that the base is the one previously reviewed. Digest-pinning the FROM lines makes any base change reviewable in a PR diff.

4. Release tag re-point at GHCR (K-3). Precondition: a compromised maintainer account with packages:write, or force-replacement of a vX.Y.Z git tag re-running the pipeline. `ravel-server:0.10.0` then serves different bytes. Cosign-verifying consumers detect it (a new signature exists but the Fulcio identity is the same workflow, so detection actually requires digest comparison or transparency-log review: partial mitigation only); plain `docker pull` consumers, including the compose quickstart's pinned default (deploy/docker-compose/ravel.yml:53), get the new bytes silently. Digest-pinning the compose default and enabling GHCR immutable tags (now available for GitHub Packages) closes it.

5. Malicious :latest service image in CI (K-7). Precondition: compromise of minio/minio, minio/mc, floci/floci, or the telemetrygen publisher. The image executes on PR and nightly runners. Fork PRs carry a read-only token, and containers do not inherit the runner's env or token, so realistic damage is CI poisoning (false green/red, cache pollution within branch scope) rather than credential theft; on main-push runs the token exposure depends on the org default (see K-5). Low probability, contained blast radius, cheap fix (digest pins).

6. Silently unmaintained parser stack (accepted, monitored). promql-parser pulls grmtools' lrpar/lrlex plus bincode 1.x; the bincode ignore already documents the revisit condition. If promql-parser itself stalls, the PromQL surface accumulates unpatchable parser dependencies. The weekly cargo-deny runs (every non-docs PR) will surface new unmaintained advisories; the ignore list is the place to watch for growth.
