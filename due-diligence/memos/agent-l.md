# Agent L memo: documentation prosecutor and claim ledger

## Verdict

The documentation is unusually rigorous by open-source standards and mostly honest: capability claims in the README are nearly all backed by code and named tests, maturity language is restrained (no "production-ready" anywhere), and several guides volunteer their own gaps (the caching guide admits the disk tier does not work, the Kubernetes guide admits the `Progressing` condition is not emitted). But the corpus has a systemic staleness problem where behavior moved after a doc was written, and one governance-level contradiction that would mislead an operator into an unsafe belief: the format-lifecycle docs (ADR-0027's own status line, ADR-0066, segment-format.md) tell an operator that after the "first public release" a format version cannot be retired without an N/N-1 reader window and evidence-based floors, while release 0.10.0, six releases after the changelog's declared "First public release" (0.9.0), deleted the RSEG v6 reader outright with no migration path, citing a "pre-release" policy the ADR record says had already expired. An adopter reading only the docs would also be misled about: how to enable distributed query (the guide's setup examples fail startup on a renamed flag and an unparseable `tls=on` value, and document the TLS default as `off` when code defaults it to `on`); alert history being "queryable" (no shipped query surface can read it); Kubernetes readiness semantics (the guide says continuous store-health probing is a "named follow-up" when it shipped); and the per-query S3 request budget default (the normative consistency model still states the retired flat 25,000 cap). The worst single drift is the format-lifecycle contradiction; the densest drift is the distributed-query operator surface, where the flag table, the guide examples, and the architecture doc all describe a flag that no longer exists.

## Drift findings

1. **Format-lifecycle governance contradicts the shipped 0.10.0 reader (worst finding).** The record says the single-version policy died at first public release: ADR-0027:3 carries "Status: Accepted (superseded at first public release by ADR-0066)", ADR-0066:60 says "superseded at (and only at) first public release ... From then on ... N/N-1", and ADR-0066:92 makes deleting a version's read support legal "only when every bucket's floor exceeds V — a checkable fact". CHANGELOG.md:182 declares 0.9.0 the "First public release". Yet 0.10.0 deleted the v6 reader under "the pre-release regime of ADR-0027" (ADR-0092:5-8), and ADR-0092:240-249 concedes "the `maintain migrate` job cannot rewrite v6 objects into v7, because a single-version reader cannot open its own inputs. That is the intended pre-release behavior". Code confirms: crates/ravel-segment/src/format.rs:129 accepts v7 only. docs/segment-format.md:2-4 and span-segment-format.md:15 still describe the deployment as "until the first public release" / "pre-release". No superseding or amending note was added to ADR-0066, and adrs/README.md:32 lists ADR-0027 as plain "Accepted". Consequence: an operator who ingested data on 0.9.x and upgrades to 0.10.0 finds every stored metrics segment unreadable (typed `UnsupportedVersion`, fail-closed), with no migration path; retention will eventually delete the unreadable objects (expiry evaluation needs no data-object reads, consistency-model.md:609-616), converting "unreadable" into permanent loss on schedule. The changelog discloses the behavior plainly (CHANGELOG.md:36-39), which is why this is a documentation-governance finding rather than a hidden data-loss bug, but the doc set an adopter would use to assess upgrade safety says the opposite of what the binary does.

2. **The distributed-query operator surface documents a flag that no longer exists and a TLS spelling the parser rejects.** `--fragment-auth-token-file` appears in distributed-query.md:177,185,273, operations.md:54, and architecture.md:302; config.rs:748-750 replaced it with `--fragment-key-file` and config.rs:2092-2094 errors with the new name. The federation example's `tls=on` (distributed-query.md:274-275) is rejected by parse_bool_field (config.rs:1174-1181, `true`/`false` only), and the guide's table documents `tls` default `off` (line 287) when the code default is `on` (config.rs:1767, test at 3406). Consequence: both "Turning it on" examples in the guide fail startup verbatim; an operator reading the table also gets the wrong (less safe) belief about the plaintext default, though the code errs safe. operations.md is internally inconsistent (old flag in the table at line 54, new flag in an example at line 1233).

3. **The alerting engine is advertised but undocumented, and its "queryable" history has no read path.** README.md:51 advertises alert transitions as "immutable, queryable data" and README.md:180-184 says the query guide covers alerting; query.md contains zero alerting content, no guide documents `--alert-rules-file` or any sink flag (operations.md's "All flags" table omits all seven alerting flags), and no shipped endpoint or CLI command reads alert history back (SessionTable in crates/ravel-sql/src/session.rs:114-125 admits only samples/logs/spans; the alerts/audit providers are dead code, as docs/guides/caching.md:33-36 admits). Consequence: an adopter choosing Ravel for auditable alert history can write it but not read it, and cannot even configure the engine without reading config.rs source.

4. **The normative consistency model has three stale statements.** (a) consistency-model.md:2-3 points at a nonexistent tests/failure/ directory (the suite is crates/ravel-failure-tests/tests/). (b) Line 86-87 states the per-query S3 request budget default as 25,000; ADR-0075 replaced that with a derived budget (crates/ravel-query/src/config.rs:63-79) and the code literally names 25,000 `OLD_FLAT_CAP` (segment_admission.rs:91). (c) Lines 137-138 state "Compaction is a verbatim page copy for every signal and never dedups"; since ADR-0092 (0.10.0) the metrics L1 compactor merges runs (CHANGELOG.md:40-47). The doc's own contract ("If code and this document disagree, one of them is a bug") makes these first-class defects. Consequence of (b): an operator sizing S3 rate limits or diagnosing `RequestBudgetExceeded` 422s reasons from a number the code retired; of (c): an operator reasoning about compaction blast radius or the conservation gate gets the wrong mechanism (the conservation property itself still holds).

5. **kubernetes.md describes pre-ADR-0050-section-7 readiness.** kubernetes.md:316-320 says continuous store-health probing is "a separate decision and a named follow-up, not an oversight"; the follow-up shipped: readiness is the AND of the startup latch and a background `sys/tenancy` probe (lib.rs:1827-1836), with `ravel_store_reachable` exported and a default alert rule (operations.md:1432). Consequence: an operator debugging readiness 503s during an S3 outage is told readiness only reflects startup and looks in the wrong place; architecture.md:101-120 has the correct description.

## Failure scenarios

1. **The stranded-upgrade operator.** An operator runs 0.9.5 in production with 90-day retention, reads segment-format.md and ADR-0066, concludes format bumps are migration-safe post-release, and upgrades to 0.10.0 during a quiet window. Every metrics query over pre-upgrade data now fails with `UnsupportedVersion`; `maintain migrate` cannot help (ADR-0092:240-243); the only options are rolling back the binary or losing history, and retention will physically delete the unreadable v6 objects on schedule if they wait. Only the changelog, not the format docs or ADR statuses, warned them.

2. **The distributed-query rollout that never starts.** An operator follows distributed-query.md "Turning it on" verbatim: `--fragment-auth-token-file /etc/ravel/fragment.token` fails startup (unknown flag). After fixing that from the error message, the federation example fails again on `tls=on`. Having read the guide's table ("tls ... default off"), they then write `tls=false` explicitly on an internal link "to match the documented default they thought they were already running", downgrading a hop the code would have defaulted to TLS.

3. **The compliance adopter who cannot read alert history.** A team picks Ravel because README.md:51 promises alert transitions as "immutable, queryable data" for audit. They configure rules (after discovering the flags exist only in config.rs source, since no guide documents them), alerts fire and are durably recorded, and at audit time they find no endpoint, SQL table, or CLI command that returns a single historical transition.

4. **The on-call engineer misled about readiness.** During an S3 outage, every pod's `/readyz` flips 503 after four probe failures and Services eject the pods. kubernetes.md:316-320 tells the on-call that readiness reflects only startup and store probing does not exist, so they burn the incident's first hour suspecting config or crash loops instead of reading `ravel_store_reachable`.

5. **The capacity planner using the phantom budget.** An operator sizes per-query S3 request expectations and provider rate limits from consistency-model.md's "default 25,000". On an 8-shard deployment the real derived budget is roughly 91,400 (8 x 10,800 + 5,000 at the 500 ms reference cadence), and their throttling math is off by nearly 4x.

6. **The dashboard that silently shows nothing.** An operator builds a stream-cap panel and alert on `ravel_admission_active_streams` from operations.md:1767. The family does not exist, the query returns empty, and the alert can never fire; the actual signal is inside `ravel_admission_active_series` dimensioned by `signal`.
