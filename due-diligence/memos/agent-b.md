# Agent B: Object-store durability and failure semantics

Scope: commit publication protocol, object-store contract and adapters, retry/idempotency, ambiguous responses, checksums, multipart, orphan handling, store qualification. Frozen commit 527a16db2e4d47b2924e4de4a4db32d7583fda33. All line numbers verified by reading the files at this commit.

## Verdict

The two-object commit protocol is implemented as documented and is sound against the contract it is written to. VERIFIED: acknowledgement is sent only after both the data-object PUT and the commit-record PUT have succeeded (or been verified idempotent by content-hash comparison), all keys are derived from a flush identity pinned before the first PUT, and no durability or recovery path reads local state. "A crash/restart cannot lose acknowledged data" is justified as a claim about process crashes, conditional on the backend honoring the contract (conditional PUT, strong read-after-write, strong and complete LIST). It is not, and is not claimed to be, protection against bucket loss, lifecycle misconfiguration, credential compromise, or a backend that violates the contract; the codebase itself documents that boundary (ADR-0058, ADR-0077, docs/consistency-model.md).

The two most consequential residuals: (1) Ravel's own orphan sweeper converts an out-of-band loss of commit records (or a persistently incomplete commit-prefix LIST) into permanent deletion of acknowledged data after ~25 h, with a circuit breaker that only catches mass loss (ADR-0058 calls this "the most dangerous flaw in the durability posture" and ships partial mitigations); (2) acknowledged-durable does not mean verified-stored: no upload checksum reaches the wire and no post-PUT ETag comparison is done, so bytes corrupted between the local CRC pre-flight and S3 storage are acked and only discovered at read time as a typed error.

## Evidence

Publication protocol (from code, not docs):

- Data PUT: `put_data_object` PUTs `CreateIfAbsent` with a local CRC32C pre-flight; `AlreadyExists` is success because the key embeds writer_id/epoch/seq/hash16 and only a prior attempt of the same pinned flush can have created it. Single attempt per call; the ingest loop owns retry. crates/ravel-commit/src/publish.rs:150-187.
- Commit PUT: `publish` PUTs the encoded record `CreateIfAbsent` at a key derived from the record's own identity fields (`commit_key_for_record`); on `AlreadyExists` it GETs the existing record and compares `content_hash`: equal is idempotent success, different is fatal `SplitBrain`. crates/ravel-commit/src/publish.rs:71-148; keys derived only from identity, crates/ravel-commit/src/keys.rs:205-267, 477-494.
- Ack point: `FlushCtx::run_flush` acks waiters with the commit token only after `publish_with_retry` returns a token; every failure path nacks. crates/ravel-ingest/src/shard.rs:529-588 (data PUT at 529, ack at 570-577). Log and span shards mirror this (crates/ravel-ingest/src/log_shard.rs:368, 509; span_shard.rs:276, 416).
- Pinned identity: seq, hour bucket, flush-open clock, and deadline are fixed before the flush task runs; serialization and blake3 happen once; retries reuse the same key and bytes. crates/ravel-ingest/src/shard.rs:420-442, 1190-1233. `SplitBrain` from the store panics the shard actor (fail loud, propagated so the router observes a dead shard). crates/ravel-ingest/src/shard.rs:758-767, 813-824.
- Writer identity: fresh UUIDv4 writer_id per generation (OS entropy in production), epoch = wall-clock seconds at generation creation, seq monotonic per shard actor. Cross-process key collision requires a UUID collision; epoch reuse is irrelevant because writer_id is fresh. crates/ravel-ingest/src/router.rs:97-131, shard.rs:1190-1191. Restart-from-empty-state is tested: crates/ravel-failure-tests/tests/retry_and_restart.rs:149 (`restart_from_empty_local_state_sees_both_writer_generations`).

Contract and adapters:

- `ObjectStoreBackend` with `PutMode::{Overwrite, CreateIfAbsent, CasVersion}`, typed error taxonomy, and `is_retryable()` (Throttled/Timeout/Transient only). crates/ravel-object-store/src/lib.rs:53-62, 382-413.
- S3 adapter maps conditional-put failures mode-aware regardless of whether the backend reported 409 or 412 (crates/ravel-object-store/src/s3.rs:362-373); `Version` is always the response ETag, never `PutResult::version`, so CAS works on versioned buckets (s3.rs:18-27, 516-526); `Error::Generic` classification is typed-first (HttpErrorKind) with a Display-text fallback for 429/503, all outcomes retryable, never Permanent (s3.rs:449-495), pinned by unit tests including the `retry_timeout`-substring shadowing regression (s3.rs:1302-1333).
- Conditional puts never route through multipart: `put` takes the multipart path only under `Overwrite` above 16 MiB, because `CompleteMultipartUpload` cannot carry a precondition in object_store 0.14 (s3.rs:60-69, 706-714). Multipart part failure poisons the handle (non-retryable, abort-and-restart), tested at the wire (s3.rs:549-626; tests/s3_http_faults.rs:926, 1002).
- MemoryStore is the semantics oracle (atomic conditional writes under one lock, strong list; crates/ravel-object-store/src/memory.rs:218-252) and `FaultStore` injects the ambiguous cases including `DuplicateDelivery` (op applied, error returned, modeling ack loss; crates/ravel-object-store/src/fault.rs:28-35, 809-815).
- Startup gates: `check_capabilities` enforces `Capabilities::mandatory()` (services/ravel-server/src/store.rs:133, 340); `qualification::enforce` refuses any production store kind without a current `sys/qualification` record, with no fresh-bucket bypass (services/ravel-server/src/qualification.rs:74-119).
- CI runs the contract suite against MemoryStore, the decorators, and a real MinIO in a required job (.github/workflows/ci.yml:590-655; crates/ravel-object-store/tests/contract.rs).

Failure-path tests that prove the protocol rather than assert it exists: retried data PUT after apply+ack-loss commits exactly once (crates/ravel-ingest/tests/fault_tolerance.rs:35); retry storm across Timeout/Throttled/Transient on both PUT targets commits exactly once with one data object and one commit record (crates/ravel-failure-tests/tests/retry_and_restart.rs:45-139); ack lost after commit yields two durable copies deduped at query time (crates/ravel-failure-tests/tests/ack_and_duplicates.rs:48); crash-matrix rows (crates/ravel-failure-tests/tests/crash_matrix.rs:50, 130); split-brain and idempotent republish unit tests (crates/ravel-commit/src/publish.rs:237-265); corrupt reads surface typed errors, never wrong data (crates/ravel-failure-tests/tests/corruption.rs:29, 95).

## Commit protocol state machine

Identity I = (tenant, signal, shard, writer_id, epoch, seq, ingest_hour), pinned at flush open. D = data key (embeds I + hash16), C = commit key (embeds I). Grace defaults: orphan GC gate = grace 24 h + max_flush_lifetime 1 h.

| # | State | Event | Outcome in code | Externally observable |
|---|---|---|---|---|
| 1 | Flush pinned, no PUT started | process death | nothing stored | client gets no ack, retries; nothing in bucket |
| 2 | Data PUT fails, retryable | retry loop | same key+bytes retried under deadline (shard.rs:699-729) | invisible; ack delayed or nack |
| 3 | Data PUT ambiguous (client timeout, server applied) | retry | `AlreadyExists` treated as success; bytes identical by construction (publish.rs:175-178) | exactly one data object; flush proceeds |
| 4 | Data PUT budget/deadline exhausted or terminal error | abandon | nack `Abandoned` (shard.rs:533-541) | client retries whole batch under new seq; any applied PUT is an invisible orphan, GC after ~25 h |
| 5 | Data exists, commit not started, process dies | crash | orphan | invisible forever; GC after grace; client retry duplicates (crash_matrix.rs:130) |
| 6 | Commit PUT retryable error (incl. applied+ack-lost) | retry | second PUT hits `AlreadyExists`, GET compares content_hash, equal = success (publish.rs:105-147) | exactly one commit record; ack with token |
| 7 | Commit PUT `AlreadyExists`, different content_hash | split brain | fatal `SplitBrain`, ingest panics shard actor (shard.rs:758-767) | shard reported unavailable; no silent overwrite either way |
| 8 | Commit landed, ack lost (crash before ack, or client disconnect) | client retry | new flush, new seq, both copies durable | metrics dedup at query; logs/spans user-visible duplicates; opt-in idempotency marker narrows this (consistency-model.md:335-343) |
| 9 | After ack | any process crash | state lives only in the bucket; restart reads only the store | acked data queryable; strict-ack claim holds |
| 10 | Commit exists, data object unavailable/corrupt | query | NotFound/Corrupted -> SnapshotInvalidated -> one re-resolve -> typed failure | no wrong data served; availability loss until repaired |
| 11 | Concurrent writers, same key | cannot occur cross-writer (UUID); same-key race is only self-retry | conformance probe asserts loser gets `AlreadyExists`, winner bytes intact (conformance.rs:525-582) | one winner |
| 12 | Racing compactors, same bucket | `CreateIfAbsent` on the compaction record picks one winner; loser verifies same input_set_hash and converges; different hash alarms and stops (crates/ravel-maintain/src/publish.rs:1-6, 203-244) | loser's parts age out as unreferenced |
| 13 | Data prefix writable, commit prefix denied (or reverse) | AccessDenied | Permanent-class, never retried (lib.rs:407-413; s3_http_faults.rs:783), immediate nack | orphan at worst; no acked loss |
| 14 | Store returns stale read/list | contract violation | not handled beyond NotFoundBlip retry paths; relied on as mandatory capability, empirically qualified | see findings 1 and 3 |

## Failure scenarios

- Ambiguous PUT (timeout, applied server-side): handled by content-addressed idempotency on both objects. Divergent committed content from a retry is impossible while identity pinning holds; the SplitBrain check is the tripwire if it does not, and it crashes rather than picks a side. VERIFIED.
- Abandoned flush with an in-flight PUT: `bound_to_deadline` drops the future at deadline (shard.rs:672-685), but an already-sent HTTP request can still land afterward. A late data PUT is an orphan anchored on its own last_modified; a late commit PUT makes the batch visible after a nack, which is at-least-once duplication, not loss. The orphan-GC interlock (writers never publish after max_flush_lifetime) is honored with margin: transport lifetime is bounded in minutes by object_store's retry budget, GC gate is ~25 h. ANALYZED, no finding.
- Commit records lost out of band (lifecycle rule, prefix delete, backend LIST bug): data invisible immediately; orphan sweeper deletes the data objects after ~25 h. Defenses: age gate, one fresh batched re-verify LIST per pass, all-or-nothing delete behind a mass-orphan breaker requiring BOTH count >= 50 AND ratio > 10% (crates/ravel-maintain/src/sweep.rs:313-390), reconstruction CLI (services/ravel-cli/src/reconstruct.rs, ADR-0058), and identity-conservative referencing (same (writer,epoch,seq) with different hash never deleted, sweep.rs:392-426). Residual: sub-threshold loss (<= 49 records, or <= 10% of a large shard) is auto-deleted with no alarm. See finding 1.
- Data object corrupted in upload: local CRC32C pre-flight covers caller/payload mismatch only; nothing verifies bytes the server stored (no wire checksum reachable through object_store 0.14, no post-PUT ETag/MD5 comparison, and ETag is not MD5 under SSE-KMS anyway). Read path fails typed (segment crc32c hierarchy, blake3 in verify-custody/scrub per ADR-0059), never serves wrong data, but the ack already happened. See finding 2.
- Bucket-level threats: versioning without noncurrent expiration silently inverts deletion guarantees; Object Lock and lifecycle state are unobservable in-process (every production probe returns Unknown; conformance.rs:243-253, 411-421), so `--require-bucket-protection` can only warn on real backends. Strict ack never claimed to cover bucket loss; DR posture is a separate documented layer (ADR-0058/0077).

## Severity-ranked findings

1. P1. Orphan GC converts out-of-band commit-record loss into permanent deletion of acknowledged data. VERIFIED (mechanism) / acknowledged by the project (ADR-0058 context: "the most dangerous flaw in the durability posture"). The sweeper deletes record-less data objects after ~25 h based on commit-prefix LIST completeness; the breaker fires only at >= 50 candidates AND > 10% of the shard, so small or thinly spread loss (and any persistent backend LIST omission) is silently destroyed. Mitigations shipped (breaker, batched re-verify, reconstruction CLI, scrub) reduce but do not close it. crates/ravel-maintain/src/sweep.rs:313-390; docs/adrs/0058:1-40.
2. P2. Acknowledged-durable is not verified-stored: no upload integrity beyond a local CRC pre-flight. VERIFIED, documented divergence. `upload_checksum` is unsatisfiable through object_store 0.14's AmazonS3 client and deliberately not mandatory; no post-PUT ETag comparison exists. Corruption introduced between the local digest and S3 storage is acked, then surfaces at read time as typed Corrupted (loss, not wrong data). crates/ravel-object-store/src/s3.rs:45-59, 497-514, 865-902; docs/object-store-contract.md:228-257.
3. P2. Store qualification is materially thinner than the semantics correctness relies on. VERIFIED. Four probes, five sequential cycles each, once per bucket forever (CreateIfAbsent record, re-run leaves it untouched; re-check only on suite-version bump). ADR-0050 section 6's cross-page-listing and multipart-visibility probes are admittedly unimplemented (docs/object-store-contract.md:319-322). No probe covers listing completeness under pagination, delete visibility, or sustained-load consistency, which findings 1 and the catalog depend on. crates/ravel-object-store/src/conformance.rs:507-744.
4. P3. Doc/code drift in the qualification description: the contract doc claims the CreateIfAbsent probe issues "two concurrent" puts; the implementation is strictly sequential (first put awaited, then second). CONTRADICTED (doc overstates). docs/object-store-contract.md:300-302 vs crates/ravel-object-store/src/conformance.rs:525-582. Reported here per repo rule, not fixed.
5. P3. `DuplicateDelivery` (applied, ack lost) is fault-injected only on the data PUT (`/l0/`) at the ingest level; the commit PUT (`/c/`) apply-then-error path is covered only by the MemoryStore-level republish unit test, not by an injected fault through the ingest retry loop. Test-coverage gap, not a code defect. crates/ravel-ingest/tests/fault_tolerance.rs:36-40; crates/ravel-commit/src/publish.rs:237-248.
6. P3. Multipart abort is best-effort with swallowed errors (`let _ = upload.abort()`), so failed large Overwrite puts can strand billed parts; the mitigating AbortIncompleteMultipartUpload lifecycle rule is recommended, unobservable in-process, and only advisory in the probe. VERIFIED, documented. crates/ravel-object-store/src/s3.rs:615-625, 679-690; conformance.rs:384-391.
7. P3. Conditional puts are capped at the single-PUT ceiling (S3 5 GiB) by design since multipart cannot carry a precondition; a data object above it would fail permanently. Current segment sizing makes this theoretical; worth a guard if segment caps ever change. crates/ravel-object-store/src/s3.rs:706-714.
8. P3. Split-brain detection compares `content_hash` only, not whole-record equality; two records with equal hash but divergent metadata would be treated as idempotent. Unreachable while identity pinning holds; noted as a narrowness, not a defect. crates/ravel-commit/src/publish.rs:137-147.

Observations, no severity: epoch is not zero-padded in keys (lexicographic order across epoch digit widths is non-numeric), but no code orders by raw key across epochs; ordering uses parsed numeric fields and discovery uses prefix LISTs (crates/ravel-commit/src/keys.rs:235-248). `list_all` dedups across pages per the contract's may-repeat guarantee (crates/ravel-object-store/src/lib.rs:458-478); the S3 page token is the last key, resumed strictly after (s3.rs:807-830), matching the oracle.
